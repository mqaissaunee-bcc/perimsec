NAT Policies

Private addresses can't cross the internet, and public servers rarely live on public addresses. Network address translation bridges the gap. The hard part is not the translation itself but writing the Security policy that goes with it, and this module is built around getting that right every time.

    Source NAT

    Getting many private hosts onto the internet.

    7.1

    NAT types and where NAT happens

    Two directions, two purposes.

    • Source NAT changes the source address of a packet. It is mostly used for outbound traffic: private internal users, such as 192.168.1.20, reaching the internet from a public address.
    • Destination NAT changes the destination address. It is mostly used for inbound traffic: hosts on the internet reaching a server that sits on a private address, such as a web server in the extranet.

    NAT rules live at . Like Security rules they are evaluated top to bottom and the first match wins. Each rule has two halves: the original packet (match criteria: source and destination zone, destination interface, service, source and destination address) and the translated packet (what to change it to).

    Recall the packet flow from Module 6. The NAT policy lookup happens during session setup, on the packet as it arrives. The translation decided there is stored in the session and applied as the packet leaves. In between, the Security policy check sees the original addresses. That ordering produces the rule you will practice in Section 7.4:

    The rule to remember

    Security policy rules use pre-NAT addresses and the post-NAT destination zone. NAT rules use the original, pre-NAT addresses and zones.

    7.2

    Source NAT types and oversubscription

    Three ways to translate a source address, from one-to-one to many-to-one.

    TypeHow it translatesTypical use
    Static IPOne fixed address to one fixed address. The source port is unchanged. Supports the bidirectional option (Section 7.3).A server that must always appear from the same public address, for example a mail server.
    Dynamic IPOne-to-one, but each internal address takes the next available address from a pool. Only the address changes, not the port.Applications that break when the source port is rewritten, with a pool large enough for the hosts.
    Dynamic IP and port (DIPP)Many-to-one. Many internal hosts share one or a few public addresses; the firewall rewrites source ports to keep sessions apart. The translated address can be the egress interface's address or addresses you specify.Users browsing the internet. By far the most common.

    A typical outbound rule: original packet from source zone Users_Net to destination zone Internet, any address; translated packet with Dynamic IP and Port, using the interface address of ethernet1/1.

    Think of it this way

    DIPP is an apartment building with one street address. Mail for everyone comes to the same address; the apartment number (the port) gets it to the right person.

    DIPP oversubscription

    Each translated address has roughly 64,000 usable source ports. Normally each address-and-port pair can serve one session at a time. With NAT oversubscription, the firewall can reuse the same translated address and port for several sessions at once, as long as they go to different destinations, because the destination still makes each session unique. The rate (for example 2x, 4x, or 8x, depending on the model) is set at . Roughly, concurrent sessions available equals ports per address times the oversubscription rate times the number of addresses in the pool.

    Part B

    Destination NAT and policy

    Publishing servers, and writing the Security rules that go with every NAT rule.

    7.3

    Destination NAT

    Give an internal server a public face.

    Destination NAT translates the destination address of incoming traffic. A client on the internet connects to 203.0.113.50; the firewall rewrites the destination to 192.168.50.80, the web server's real address in the Extranet zone.

    The original packet

    The NAT rule matches the packet as it arrives, before translation. The source zone is where it came from (Internet). The destination zone is the zone the original destination address routes to. Because 203.0.113.50 is on the ethernet1/1 subnet, it routes to ethernet1/1, so the destination zone is also Internet. The destination address is 203.0.113.50.

    This surprises almost everyone the first time: for inbound destination NAT, the NAT rule's source and destination zones are usually the same outside zone.

    The translated packet

    • Static IP: one-to-one translation of the destination address, leaving the port unchanged unless you specify one.
    • Port translation: set a translated port when the server listens somewhere other than the well-known port, for example public tcp/80 to a server on tcp/8080. The rule's service field limits which original ports match; note that the predefined service-http includes both tcp/80 and tcp/8080.
    • Dynamic IP: the translated address can be an FQDN, address object, or address group, which suits servers with DHCP-assigned or changing addresses, and can spread connections across several servers.

    Bidirectional static NAT

    A static source NAT rule with the Bi-directional option set also creates the matching destination NAT in reverse. One rule then lets an internal server send traffic from its public address and receive connections on it. It is available only for static IP translation.

    7.4

    Writing Security policy for NAT

    One rule of thumb resolves every NAT policy question.

    The firewall checks Security policy after it has decided on the NAT translation but before it applies it. At that moment it knows two things: the packet's original addresses, which are still in the packet, and where the translated packet will go, which it has already routed. So:

    FieldNAT ruleSecurity rule
    Source zonePre-NAT (ingress zone)Pre-NAT (ingress zone)
    Destination zonePre-NAT: zone the original destination routes toPost-NAT: zone the translated destination routes to
    Source addressPre-NATPre-NAT
    Destination addressPre-NATPre-NAT

    For source NAT none of this is tricky: the destination isn't translated, so pre-NAT and post-NAT destinations are the same. For destination NAT, the Security rule mixes the two: the public address you published, and the zone where the server really lives.

    Applied to the web server example: the Security rule is source zone Internet, destination zone Extranet, destination address 203.0.113.50, application web-browsing.

    Common misconception

    "The Security rule should use the server's real address, 192.168.50.80, since that's where the traffic ends up." It won't match. When policy is checked, the packet still carries 203.0.113.50. Use the address the client connected to.

    Guided problem 7.1

    The published server nobody can reach

    You published the extranet web server with a destination NAT rule from Internet to Internet, 203.0.113.50 to 192.168.50.80. Your Security rule allows source zone Internet, destination zone Internet, destination address 192.168.50.80, web-browsing. Outside users time out. Find both mistakes.

    1. Check the NAT rule against the rule of thumb: pre-NAT zones and addresses. Internet to Internet, 203.0.113.50: correct.
    2. Check the Security rule's destination zone. It must be the post-NAT zone, where 192.168.50.80 actually lives: Extranet, not Internet. First mistake.
    3. Check the Security rule's destination address. It must be the pre-NAT address the client used: 203.0.113.50, not 192.168.50.80. Second mistake.
    4. Corrected Security rule: source zone Internet, destination zone Extranet, destination address 203.0.113.50, application web-browsing, service application-default. Confirm with Test Policy Match, then watch the Traffic log, which shows both the pre-NAT and post-NAT addresses for each session.

    Before you start

    Watch out for

    • The internal DNAT zones. 192.168.1.80 is on the users' own subnet, so the NAT rule is Users_Net to Users_Net. The Security rule is Users_Net to Extranet with destination 192.168.1.80. This is Scenario 3 in Simulation 7.1.
    • Existing sessions. A new NAT rule applies to new sessions. If a test seems to ignore your change, close the browser tab or wait for the old session to time out.
    • NAT rule order. A broad source NAT rule above the destination NAT rule can match first. Put specific NAT rules above general ones.
    • Read both addresses in the Traffic log. Add the NAT source and destination columns to see the translation actually happening.

    Summary and self-check

    • Source NAT translates the source address, usually for outbound access. Destination NAT translates the destination address, usually to publish internal servers.
    • NAT rules match the original packet and specify the translated packet. They are evaluated top-down; first match wins. Translation is decided at session setup and applied at egress.
    • Static IP is one-to-one and supports bidirectional NAT. Dynamic IP is one-to-one from a pool without port changes. DIPP shares addresses by translating ports, and oversubscription lets address-port pairs serve several destinations at once.
    • For inbound destination NAT, the NAT rule's destination zone is the zone the public address routes to, usually the same outside zone as the source.
    • Destination NAT can translate ports, and can translate to an FQDN or address group.
    • Security rules use pre-NAT addresses and the post-NAT destination zone.

    Key terms

    NAT, source NAT, destination NAT, DIPP, NAT oversubscription, bidirectional NAT.
