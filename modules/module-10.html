Security Profiles

An allow rule decides that traffic may pass. It says nothing about whether that traffic is safe. Security Profiles inspect what you allowed, catching exploits, malware, command-and-control, dangerous files, and sensitive data on their way through.

    10.1

    Content-ID and Security Profiles

    Policy decides what may pass; profiles decide whether what passes is safe.

    Recall the packet flow from Module 6: after App-ID identifies the application and Security policy allows it, Content-ID inspects the traffic using the Security Profiles attached to the matching rule. Content-ID is a stream-based threat prevention engine (Module 1's single-pass architecture) that scans for software vulnerability exploits, viruses, spyware, malicious URLs, and restricted files and data. When a profile finds something, it can allow, alert (log), block, or ask the user, depending on the profile and threat.

    Profiles attach only to rules whose action is allow. A deny rule has nothing to inspect.

    10.2

    Vulnerability Protection

    Intrusion prevention for the services you expose and the clients you protect.

    A Vulnerability Protection profile detects attempts to exploit known flaws: buffer overflows, code execution, SQL injection, and the like, in both client-to-server and server-to-client directions. PAN-OS includes two predefined profiles at :

    • default applies each signature's default action, which blocks most critical, high, and medium-severity exploits and only alerts on low and informational ones.
    • strict blocks critical, high, and medium-severity events regardless of the signature default. It is the usual best-practice starting point.

    Predefined profiles are read-only. To customize, clone one and edit the clone, or build a new profile. A profile is a list of rules, each matching signatures by severity, host type (client or server), category, or a CVE or vendor ID, and assigning an action (default, allow, alert, drop, reset client, reset server, reset both, or block IP) and a packet capture setting.

    Exceptions and inline analysis

    If one signature causes false positives, add an exception for its threat ID on the Exceptions tab, overriding the rule's action for that signature only, optionally for specific IP addresses. Inline cloud analysis engines in the profile also detect unknown SQL and command injection attempts in real time, beyond what signatures catch.

    In the field

    Turn on packet capture for critical and high-severity events. When the security team asks "was that a real attack?", the capture answers it.

    10.3

    Antivirus

    Three kinds of malware detection in one profile.

    An Antivirus profile at sets an action for each decoder (protocol) the firewall scans, such as http, smtp, ftp, imap, pop3, and smb, in three columns:

    • Signature action: for antivirus signatures delivered in Antivirus content updates.
    • WildFire signature action: for signatures generated by WildFire analysis (Module 12), which arrive much faster than the daily antivirus release.
    • WildFire inline ML action: for a real-time machine-learning scan of certain file types (such as Windows executables and Office files) that can block malware nobody has seen before, on the first download.

    Actions include default, allow, alert, drop, and the reset options. The predefined default profile is read-only; clone it to change actions. Two more tabs matter: Application Exception, to change the action for a specific application, and Signature Exceptions, where you add a threat ID (found in the Threat log) to stop a false positive.

    Exam tip

    An exception is always by threat ID. If a question asks how to stop one antivirus or vulnerability signature from blocking a legitimate application, the answer is a threat ID exception in the profile, not disabling the profile or the rule.

    10.4

    Anti-Spyware and DNS sinkholing

    Catch infected hosts by what they try to contact.

    An Anti-Spyware profile at detects command-and-control (C2) traffic: an infected machine calling home for instructions, or sending data out. Like Vulnerability Protection, it has predefined default and strict profiles, rules matching by severity and category, and exceptions by threat ID.

    DNS policies

    Malware almost always looks up its C2 server by name first, so the DNS query is an early chance to catch it. The profile's DNS Policies section sets an action for each source of malicious domains: Palo Alto Networks' DNS signatures (and the DNS Security cloud service, if licensed) and any external dynamic lists of domains you add. The best-practice action is sinkhole. The same section can also block DNS over HTTPS, which would otherwise hide lookups inside encrypted web traffic.

    How a sinkhole works

    With a DNS sinkhole, the firewall answers the malicious lookup with a sinkhole address instead of the real one: Palo Alto Networks' sinkhole.paloaltonetworks.com by default, or an internal address you choose. The infected host then tries to connect to the sinkhole, and that connection attempt identifies it.

    Finding the infected host

    The Threat log's sinkhole entry often names the wrong machine: its source is whoever sent the query to the firewall, which on most networks is the internal DNS server. To find the infected hosts, filter the Traffic log for sessions to the sinkhole address. Check daily, or schedule a report.

    10.5

    File Blocking and Data Filtering

    Keep dangerous files out and sensitive data in.

    File Blocking

    A File Blocking profile at has rules that match by application, file type, and direction (upload, download, or both) and take one of three actions:

    • alert: allow the transfer and log it.
    • continue: show the user a response page and let them choose to proceed. This works only with web-browsing.
    • block: stop the transfer, log it, and show a response page.

    Predefined profiles named basic file blocking and strict file blocking are good starting points to clone. The firewall decodes up to four levels of encoding, such as a file in an archive inside a gzip HTTP response, and can block files encoded more deeply than that, which is a common evasion trick. Blocked files are recorded in the Data Filtering log at , where source is the system that sent the file and destination is the one that received it.

    Data Filtering

    A Data Filtering profile detects sensitive data leaving (or entering) the network:

    1. Create a data pattern at : predefined patterns (credit card numbers, Social Security numbers with and without dashes), regular expressions, or file properties.
    2. Create the profile at , adding the pattern with an alert threshold and a block threshold: the number of matches in one file or transfer that triggers each action, plus a log severity.

    Thresholds keep the profile practical: one nine-digit number in a document might be a coincidence, while fifty is a spreadsheet of employee records.

    10.6

    Attaching profiles: Security Profile Groups

    One object, every rule, no forgotten profile.

    On a Security rule's Actions tab, Profile Setting can be Profiles, where you pick each profile individually, or Group, where you pick one Security Profile Group. Create groups at by choosing one profile of each type you want.

    Groups are the practical choice: every allow rule gets the same inspection, and changing a profile in the group changes it everywhere. In the rulebase, hover over the profile icons in a rule's row to see which group or profiles it uses. A group named default, if you create one, is automatically attached to new rules you add, which helps make inspection the default rather than an afterthought.

    Common misconception

    "The firewall inspects everything automatically." It inspects only traffic matching allow rules that have profiles attached. An allow rule with no profiles is a door with no one checking bags, which is what Lab 8 demonstrates before you build the group.

    Watch out for

    • The high-level steps stop early. They end at the tar-file test. The detailed steps (Task 2.12) also retest the SSN file and the dig query and review the Threat log. Do those checks whichever version you follow: they prove the data filtering and sinkhole work.
    • Six rules, one profile setting each. Every allow rule needs the group on its Actions tab, including Acquisition-Allow-All and Extranet_to_User_Net. A rule you skip is a rule with no inspection.
    • Let the script finish. It runs for about 6 minutes; interrupting it means fewer Threat log entries to study.
    • The sinkhole result looks like a failure. dig returning sinkhole.paloaltonetworks.com instead of quora.com's address is success. The EDL lists quora.com and producthunt.com only for the lab; they aren't really malicious.
    • Where the source address points. In the Threat log, the DNS event's source is whoever sent the query. Here that's the client itself, because it queried 8.8.8.8 directly; in a network with an internal DNS server it would be the DNS server (Simulation 10.2).

    Summary and self-check

    • Content-ID applies Security Profiles to traffic allowed by Security policy. The seven types are Antivirus, Anti-Spyware, Vulnerability Protection, URL Filtering, File Blocking, Data Filtering, and WildFire Analysis.
    • Vulnerability Protection, Antivirus, and Anti-Spyware log to the Threat log; File Blocking and Data Filtering log to the Data Filtering log.
    • Predefined profiles (default, strict) are read-only; clone to customize. Rules set actions by severity and category; exceptions override by threat ID.
    • Antivirus has signature, WildFire signature, and WildFire inline ML actions per decoder.
    • Anti-Spyware detects C2 and sinkholes malicious DNS lookups. Find infected hosts in the Traffic log by filtering for the sinkhole address, because the Threat log source is often the DNS server.
    • File Blocking controls file types with alert, continue (web-browsing only), or block. Data Filtering uses data patterns with alert and block thresholds.
    • Security Profile Groups apply consistent inspection to every allow rule.

    Key terms

    Content-ID, Security Profile, Vulnerability Protection, Antivirus profile, Anti-Spyware profile, DNS sinkhole, File Blocking, Data Filtering, data pattern, Security Profile Group, Threat log.
