Managing Firewall Configurations

A firewall keeps two versions of its configuration at all times: the one that is protecting the network and the one you are editing. Knowing exactly which is which, and how to save, roll back, and audit both, is what separates a confident change from an outage.

    Part A

    Two configurations

    Running, candidate, and the operations that move configuration between them.

    3.1

    Running and candidate configurations

    Everything you do in the web interface or CLI changes a working copy, not the live firewall.

    • The running configuration is what the firewall is enforcing right now.
    • The candidate configuration is the working copy that holds changes in progress. It starts identical to the running configuration and diverges as you edit.

    A commit validates the candidate and, if it is valid, makes it the new running configuration. Until then, the network is unaffected by anything you have typed.

    The candidate lives in memory. If the firewall reboots before you commit or save, uncommitted changes are lost. That is why PAN-OS gives you a save operation that writes work in progress to disk without activating it.

    Think of it this way

    A shared document with a draft and a published version. Editing changes the draft; nobody reading the published version sees a thing until you press Publish. Commit is Publish. Save is saving the draft so a crash does not lose it.

    3.2

    Commit, preview, and validate

    Commit is the moment of truth, so PAN-OS gives you tools to look before you leap.

    Whose changes get committed?

    The candidate is shared. If two administrators are editing at once, both sets of changes sit in the same candidate. When you click Commit, you choose:

    • Commit all changes: everything pending from every administrator. This requires the permissions to commit other people's work.
    • Commit changes made by specific administrators, typically just yourself. Other people's pending changes stay in the candidate, untouched.

    Look before you commit

    • Preview Changes shows a side-by-side comparison of the candidate and the running configuration.
    • Change Summary lists each object and setting you are about to change.
    • Validate Commit runs the same checks as a commit and shows any errors, without applying anything.

    Reading the result

    The Commit Status window reports the result. Errors stop the commit; nothing changes until you fix them. Warnings do not stop the commit, but read them: they include shadowed Security policy rules (Module 6) and unresolved application dependencies (Module 8). If you close the window, reopen it with the Tasks button at the lower right.

    Every successful commit also saves a timestamped copy of the new running configuration as a configuration version. That version history is your rollback path.

    Exam tip

    Warnings never block a commit; errors always do. A question that says "the commit succeeded with warnings" means the change is live.

    3.3

    Save, revert, load, export, and import

    The operations at , and when to use each.

    These operations act on the whole firewall configuration, not just one administrator's changes. Revert, save, and load work with files stored on the firewall. Export copies a file from the firewall to your computer; import copies one from your computer to the firewall.

    OperationWhat it doesUse it when
    Save candidate configurationWrites the candidate to the default file, snapshot.xml, overwriting it.You are mid-change and want to protect your work without activating it.
    Save named configuration snapshotWrites the candidate to a file you name.You want a labeled restore point, such as before-nat-changes.xml.
    Revert to last saved configurationReplaces the candidate with snapshot.xml.Your recent edits went wrong and you want your last saved state back.
    Revert to running configurationReplaces the candidate with the running configuration, discarding all uncommitted changes.You want to throw away everything pending and start over.
    Load named configuration snapshotReplaces the candidate with a named file (or the running config, or snapshot.xml).Restoring a labeled restore point or a lab baseline.
    Load configuration versionReplaces the candidate with an earlier running configuration from the commit history.Rolling back a commit that caused problems.
    Export named snapshot or configuration versionDownloads the file to your computer.Off-box backups, before upgrades, sharing with support.
    Import named configuration snapshotUploads a file from your computer to the firewall as a named snapshot.Restoring a backup or loading a configuration built elsewhere.

    Common misconception

    "Loading a configuration rolls the firewall back." Load and revert change only the candidate. The firewall keeps enforcing the old running configuration until you commit. This is also why an import never changes anything by itself: import puts the file on the firewall, load puts it in the candidate, and commit makes it run.

    There is also a per-administrator version of save and revert under the Changes button at the upper right of the web interface. Revert Changes there (and the related save options) can apply to all changes or only your own, which is handy when you share the firewall with others.

      Part B

      Teams and audit trails

      Working safely alongside other administrators, and proving who did what.

      3.4

      Multiple administrators and locks

      When several people manage one firewall, locks keep them from stepping on each other.

      • A configuration lock blocks other administrators from changing the candidate configuration.
      • A commit lock blocks other administrators from committing. They can still edit, but their changes wait until the lock is released.

      Set and remove locks from the lock icon at the top of the web interface. The administrator who set a lock can remove it, and a superuser can remove anyone's lock, for example when a colleague leaves for the day with a lock still in place. You can also configure PAN-OS to take a commit lock automatically as soon as an administrator starts changing the candidate (Automatically Acquire Commit Lock, under ).

      In the field

      Use a commit lock during a change window when you are making a series of changes that must go live together. It stops a colleague's well-meaning "commit all" from activating half of your work.

      3.5

      System and Configuration logs

      Every change and every commit leaves a record. Learn to find it.

      All log types are under . Two matter most when managing configuration:

      • The System log records system events: commits and their results, administrator logins and failed logins, content and software installs, interface and HA changes, and hardware alerts.
      • The Configuration log records each configuration change: the administrator, the client used (web, CLI, or API), the source address, the object path that changed, and the before and after values.

      Filtering

      Logs get long fast, so filter. The quickest way is to click any value in a log entry, such as an administrator's name; PAN-OS adds it to the filter bar. Apply the filter with the arrow icon and clear it with the X. Filters use the form ( field operator value ) and combine with and and or:

      # Configuration log: everything admin-bob changed
( admin eq admin-bob )

# Configuration log: admin-bob's changes since October 1
( admin eq admin-bob ) and ( receive_time geq '2026/10/01 00:00:00' )

      The Filter Builder (the plus icon next to the filter bar) lets you pick fields, operators, and values from lists instead of typing them, which is the best way to learn the syntax. You can also export the filtered results to a CSV file.

      ✓

      Summary and self-check

      • The running configuration is active; the candidate holds pending changes. Only a commit makes the candidate run.
      • You can commit all changes or only selected administrators' changes. Preview Changes, Change Summary, and Validate Commit let you check first. Errors block a commit; warnings do not.
      • Save writes the candidate to snapshot.xml or a named file. Revert, load, and import change the candidate or the files on the firewall, never the running configuration on their own.
      • Each commit creates a configuration version you can load later to roll back.
      • Config locks block edits; commit locks block commits. Superusers can remove anyone's lock.
      • The System log records events such as commits and logins; the Configuration log records who changed what, with before and after values. Filter by clicking values or with the Filter Builder.

      Key terms

      Running configuration, candidate configuration, commit, configuration snapshot, configuration lock, commit lock, System log, Configuration log.
