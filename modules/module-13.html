Encrypted Traffic and Decryption

Most web traffic is now encrypted, and so is most malware delivery. Everything you built in Modules 8 through 12 works only on what the firewall can see. This module teaches the certificates and policies that let the firewall look inside, and the judgment about when it shouldn't.

    Part A

    Certificates

    Why decryption is needed, and the trust system it depends on.

    13.1

    Why decrypt, and how TLS works

    You can't analyze what you can't see.

    TLS (still often called SSL) protects traffic in three ways: encryption for privacy, hashes for integrity, and certificates for authentication. Those same protections hide malware coming in and data going out. Without decryption, the firewall sees addresses, ports, the server name the client asks for, and the server's certificate; App-ID can often name the application from that. Antivirus, Vulnerability Protection, File Blocking, Data Filtering, and WildFire see only ciphertext. Simulation 10.1 showed the gap: malware over HTTPS passed every profile.

    A quick TLS review

    1. The client asks the server for a secure connection.
    2. The server sends its certificate: its public key, signed by a certificate authority (CA).
    3. The client checks the certificate against the CAs in its trusted root store.
    4. The client sends a session key, protected so that only the server's private key can recover it (or the two sides derive one together).
    5. Both sides switch to fast symmetric encryption with the session key.

    Decryption works by putting the firewall in the middle of that exchange, with the client's consent through its trust store (outbound) or the server owner's consent through its private key (inbound).

    Three kinds of decryption

    TypeProtectsHow
    SSL Forward ProxyInternal users reaching external serversThe firewall is a proxy: it makes its own connection to the server and presents the client with a certificate it signed.
    SSL Inbound InspectionYour own servers receiving connectionsNo proxy: the firewall holds a copy of the server's certificate and private key and decrypts as traffic passes.
    SSH ProxySSHv2 sessionsThe firewall proxies SSH to detect and control tunneling.
    13.2

    PKI and certificates on the firewall

    Who vouches for whom.

    A public key infrastructure (PKI) answers the question "is this really the server's public key?" A root CA certifies intermediate CAs, which issue certificates to devices and servers. Each certificate carries the owner's name, public key, validity dates, intended uses, serial number, and the issuer's digital signature. A client trusts a certificate if it can follow the signatures up this chain to a root in its certificate store.

    Checking certificates

    To validate a certificate, the firewall checks each certificate in the chain: is the signature valid, is it within its date range, is it well formed, and has it been revoked? Certificates are revoked when a private key is compromised, the owner's name changes, a host is decommissioned or an employee leaves, or a counterfeit is found. Revocation is checked with a CRL (certificate revocation list) or OCSP (Online Certificate Status Protocol), configured at .

    Getting certificates onto the firewall

    At you can generate, import, export, renew, revoke, and delete certificates, and set what each one is used for. The table shows the hierarchy, so you can see each chain. Three ways to get a CA certificate for decryption:

    • Self-signed: Generate, leave Signed By blank, and select Certificate Authority. Quick, as in Lab 12, but every client must be told to trust it.
    • Import a certificate and private key created by your internal CA.
    • CSR: the firewall generates a key pair and a certificate signing request; your enterprise CA signs it as a subordinate CA; you import the signed certificate. The private key never leaves the firewall, and clients that already trust your enterprise root automatically trust the firewall. This is the best practice for production.

    Forward Trust and Forward Untrust

    SSL Forward Proxy needs two CA certificates, marked by checkboxes on the certificate:

    • The Forward Trust certificate signs the firewall's copy of a server certificate that was valid. Clients must trust it, or every decrypted site shows a warning.
    • The Forward Untrust certificate signs the copy when the server's certificate was not valid: expired, self-signed, or from an untrusted CA. Clients must not trust it, so users still see the warning the original certificate deserved. Without it, decryption could hide a bad certificate behind a trusted one.

    Think of it this way

    The firewall is a notary re-stamping documents for the office. Genuine documents get the office's trusted stamp. Doubtful ones get a stamp that says "DO NOT TRUST" in red. A notary with only one stamp would be dangerous.

    13.3

    Configuring SSL Forward Proxy

    Certificates, then a rule, then a profile, then client trust.

    1. Certificates: a Forward Trust CA certificate and a Forward Untrust CA certificate (Section 13.2).
    2. Decryption policy rule at : match on source and destination zones and addresses, users, service, and URL category; set the action to decrypt and the type to SSL Forward Proxy. Decryption rules decide what to decrypt; a Security policy rule must still allow the traffic.
    3. Decryption profile at , attached to the rule: additional certificate and protocol checks, such as blocking sessions with expired certificates or untrusted issuers, blocking unsupported cipher suites, and setting the minimum and maximum TLS versions (including TLS 1.3; older versions and algorithms are no longer considered secure).
    4. Client trust: deploy the Forward Trust CA certificate to clients' trusted root stores, through Group Policy, MDM, or by hand.

    Phase decryption in gradually, a few categories or user groups at a time, and watch the Decryption log for sites that break. Remember SSL on non-standard ports when writing match criteria.

      13.4

      Inbound inspection and exclusions

      Decrypting traffic to your own servers, and choosing what never to decrypt.

      SSL Inbound Inspection

      For connections from the internet to your own HTTPS servers, the firewall doesn't need to impersonate anyone: you own the server. Import the server's certificate and private key at Device > Certificate Management > Certificates, then create a Decryption rule with type SSL Inbound Inspection that names the certificate. The firewall decrypts and inspects as traffic passes, so Vulnerability Protection can catch attacks aimed at the server. The inbound Decryption profile has resource checks too; by default it lets encrypted traffic through undecrypted if the firewall is too busy to decrypt it.

      What not to decrypt

      • The SSL Decryption Exclusion list at lists sites known to break under decryption, typically because applications pin their certificates or require client certificates. Palo Alto Networks maintains entries through content updates, and you can add your own. Exclusions apply regardless of Decryption policy.
      • No-decrypt rules: a Decryption rule with action no-decrypt, usually matching URL categories such as financial-services and health-and-medicine, placed above the decrypt rule. Legal, privacy, HR, and regional rules often require this. A Decryption profile on a no-decrypt rule can still block sessions with expired or untrusted certificates.

      In the field

      Decryption is a policy decision as much as a technical one. Before turning it on, get agreement from legal, HR, and privacy staff, tell users through the acceptable use policy, and document which categories are exempt and why.

      13.5

      Troubleshooting decryption

      When a site breaks after you turn on decryption, the logs say why.

      • The Decryption log at records the TLS details of each session: version, cipher, certificate information, and errors such as a handshake failure or an untrusted issuer.
      • ACC > SSL Activity summarizes decrypted and undecrypted traffic, versions, and failures.
      • The Traffic log has a Decrypted column, and the Session End Reason column shows why a session ended, such as threat or decrypt-error. A useful filter for decrypted sessions ended by a detected threat:
      ( flags has proxy ) and ( session_end_reason eq threat )

      Guided problem 13.1

      "Every website shows a security warning"

      You enable an SSL Forward Proxy rule for all users. Within minutes the help desk reports that every HTTPS site shows a certificate warning. Work out the cause and the fix.

      1. Every site, not some, points to something that affects all decrypted sessions equally: the certificate the firewall presents.
      2. For valid sites the firewall presents copies signed by its Forward Trust CA. The browser warns if it doesn't trust that CA.
      3. So clients don't have the Forward Trust CA in their trusted root stores. Check a warning's certificate details: the issuer will be the firewall's CA.
      4. Fix: deploy the Forward Trust CA certificate to clients (Group Policy or MDM in production; Lab 12 does it by hand in Firefox). Better still, use a CSR so the firewall's CA is subordinate to an enterprise root clients already trust.
      13.6

      SSH proxy and other decryption features

      Beyond TLS.

      • SSH proxy: a Decryption rule of type SSH Proxy decrypts SSHv2 sessions using a key the firewall generates, so App-ID can tell ordinary ssh from ssh-tunnel, which carries other traffic inside SSH. Write Security rules that allow ssh and deny ssh-tunnel. It doesn't support SSH sessions that use passwordless key login.
      • Decryption port mirroring copies decrypted traffic out a dedicated interface to tools such as data loss prevention or forensic recorders. It requires a free license.
      • Network Packet Broker (which replaced Decryption Broker) forwards decrypted, undecrypted, and non-TLS traffic through a chain of other security tools, controlled by Packet Broker profiles.
      • Hardware security modules (HSMs) store keys in tamper-resistant hardware. The firewall can use one for the Forward Trust key, private keys for inbound inspection, and its own master key.

      Reasons not to decrypt some traffic

      Some traffic shouldn't or can't be decrypted: privacy-sensitive categories, applications that pin certificates or need client authentication, regulated data in some jurisdictions, and traffic beyond what the firewall's hardware can decrypt at the needed rate. Decryption is resource-intensive; size firewalls for it.

      2. Before decryption: http://192.168.50.80/eicar.com is blocked (the Antivirus profile sees it in clear text). The same test file from www.eicar.org over HTTPS downloads. Cancel the save.
      3. Certificates at : generate trusted-cert (common name 192.168.1.1, Certificate Authority, Forward Trust Certificate) and untrusted-cert (common name DO NOT TRUST, Certificate Authority, Forward Untrust Certificate).
      4. Decryption rule Decrypt_User_Traffic at : Users_Net to Internet and Extranet, action Decrypt, type SSL Forward Proxy. Commit. Browse to https://www.bing.com and see the firewall (192.168.1.1) as the certificate issuer, with a browser warning.
      5. Make the client trust it: export trusted-cert as Base64 (PEM), import it in Firefox's Certificate Manager under Authorities, and trust it to identify websites. Then visit https://192.168.50.80, whose self-signed certificate makes the firewall present DO NOT TRUST.
      6. Retest: the HTTPS download of eicar.com is now blocked. In the Traffic log add the Decrypted column, move Session End Reason to the front, and filter with ( flags has proxy ) and ( session_end_reason eq threat ). Find the matching Threat log entry.
      7. Exempt categories: a No-Decryption rule at the top (government, financial-services, shopping; action No Decrypt). Commit, browse to https://texas.gov, and confirm the issuer is not 192.168.1.1.

      Watch out for

      • The high-level steps leave out the untrust certificate. Creating untrusted-cert (Task 2.4) and testing it against the extranet server's self-signed certificate (Task 2.9) appear only in the detailed steps. Do them either way: a forward proxy without a Forward Untrust certificate is incomplete (Section 13.2).
      • The warnings are expected, twice. Before you import trusted-cert, every decrypted site shows a warning because the client doesn't trust the firewall's CA. After you import it, https://192.168.50.80 still warns, correctly, because the server's own certificate is untrustworthy and the firewall is passing that on.
      • Import into Authorities, not Your Certificates. Firefox keeps CA certificates under Authorities. Check the box to trust it to identify websites, or nothing changes.
      • Two test paths for eicar over HTTPS. The high-level steps use www.eicar.org; the detailed steps use https://192.168.50.80/eicar.com. Either shows decryption working.
      • Rule order. No-Decryption must sit above Decrypt_User_Traffic, or the decrypt rule matches first and the exemption never applies.
      • Privacy is a real concern. The guide's note is worth reading: which categories you exempt depends on company policy, privacy law, HR, and the destination's country.

      Summary and self-check

      • Without decryption, threat profiles and WildFire can't inspect encrypted content. TLS uses certificates for authentication and keys for encryption.
      • Certificates chain to trusted roots and are checked for signature, dates, form, and revocation (CRL, OCSP). Generate, import, or use a CSR at Device > Certificate Management > Certificates.
      • SSL Forward Proxy needs a Forward Trust CA (trusted by clients) and a Forward Untrust CA (never trusted), a decrypt rule, a Decryption profile, and client trust deployment.
      • SSL Inbound Inspection uses your server's certificate and private key, with no proxy.
      • The SSL Decryption Exclusion list overrides policy; no-decrypt rules exempt categories and still allow certificate checks.
      • Troubleshoot with the Decryption log, ACC SSL Activity, and Traffic log columns such as Decrypted and Session End Reason.
      • SSH proxy separates ssh from ssh-tunnel. Port mirroring, Network Packet Broker, and HSMs extend decryption.

      Key terms

      SSL Forward Proxy, SSL Inbound Inspection, Forward Trust certificate, Forward Untrust certificate, Decryption profile, SSH proxy, HSM, certificate signing request.
