User-ID

An IP address tells you which machine sent a packet. It doesn't tell you who was sitting at it, and on networks with DHCP, VPNs, and shared servers it doesn't stay put. User-ID ties traffic to people and groups, so policy can say "marketing may use social media" and the logs can say who did what.

    Part A

    How User-ID knows who

    The two mappings, the agents that build them, and the many places identity comes from.

    9.1

    What User-ID does

    Two lookups turn an address into a name and a name into groups.

    User-ID lets you write policy, read logs, and run reports by username and group instead of IP address. It does that with two functions:

    • User mapping associates an IP address with a username: 10.20.1.11 is acme\alee, right now.
    • Group mapping learns from an LDAP directory which groups each user belongs to: alee is in marketing.

    When a session arrives, the firewall looks up the source address to find the user, looks up the user to find the groups, and evaluates policy with all three. The Traffic log then shows the source user alongside the address.

    Components

    ComponentWhat it does
    The firewallHolds the IP-to-user and user-to-group mappings and enforces policy with them.
    PAN-OS integrated User-ID agentRuns on the firewall itself and collects IP-to-user information, for example by reading domain controller logs.
    Windows-based User-ID agentSoftware installed on a Windows domain member that collects the same information and sends it to the firewall.
    Terminal Services agentRuns on Microsoft and Citrix terminal servers and maps IP address plus source port ranges to users, because many users share one address.

    Integrated or Windows-based agent?

    Both monitor the same domain controllers. The difference is where the work happens and what crosses the network. The integrated agent pulls the domain controllers' Security log events to the firewall and extracts logins there. A Windows-based agent does the extraction near the domain controllers and sends the firewall only the resulting IP-to-user mappings, a small fraction of the data. For a remote site with its own domain controllers and a slow link, either install a Windows-based agent at that site or use the integrated agent on that site's local firewall.

    9.2

    User mapping methods

    Identity comes from wherever users prove who they are. A real deployment uses several sources at once.

    If you haveUseHow it learns users
    Domain controllers, Exchange, or eDirectory serversServer monitoring (User-ID agent)Reads login events from the servers' logs. On by default when you add a server.
    Windows file and print serversSession monitoring (User-ID agent)Reads users' sessions to shared files and printers, keeping known mappings fresh.
    Windows clients that change addresses oftenClient probing (User-ID agent)Asks the client who is logged in, with WMI (the integrated agent supports only WMI probing).
    Remote users on GlobalProtectGlobalProtectUsers must log in to connect, so the username is known for certain. The best choice for high-security environments.
    Non-Windows systems, wireless controllers, 802.1X, NAC, proxiesSyslog listeningParses login messages those systems send, using Syslog Parse Profiles to read each vendor's format.
    Users who sign in to nothing else, such as guestsAuthentication PortalPrompts for credentials when web traffic arrives from an unmapped address.
    Citrix or Remote Desktop serversTerminal Services agentMaps each user's port range on the shared address.
    Systems with no built-in integrationXML APIAnother system pushes mappings to the firewall.
    Users behind an upstream proxyXFF headersReads the client address the proxy adds in the X-Forwarded-For header.

    In the field

    Client probing sends a query, with the agent's credentials, to whatever address it is trying to map. Never enable it on zones that include untrusted networks, and many organizations avoid it entirely in favor of server monitoring plus GlobalProtect.

    Part B

    Configuring and using User-ID

    Turning it on, connecting it to the directory, and putting names in policy.

    9.3

    Enabling User-ID and the integrated agent

    Four steps: enable by zone, configure mapping, optionally configure group mapping, then use names in policy.

    Enable User-ID per zone

    At , open the zone where user traffic originates and select Enable User Identification. The firewall then maps users only for traffic from that zone. By default every subnet in the zone is mapped; Include and Exclude lists narrow that. Enable it only on internal zones, never on a zone facing the internet.

    Exam tip

    User-ID is enabled on the source zone, where users are, not on the destination zone they are reaching. If the Source User column is empty, check the zone setting first.

    Configure the integrated agent

    1. Create a service account in the domain for the agent. Membership in Domain Admins works, but least privilege is better: Server Operators plus Event Log Readers gives the permissions it needs.
    2. Define the servers to monitor at . Discover finds domain controllers automatically; Add is required for Exchange, eDirectory, and syslog senders.
    3. Enter the service account in the agent setup, so the firewall can read the servers' logs. Server monitoring is on by default.
    4. Optionally enable session monitoring and WMI client probing on the same page.
    5. Commit and verify: each monitored server's status should show Connected under Device > User Identification.

    To see the mappings themselves, check or the CLI:

    admin@PA-VM> show user ip-user-mapping all
admin@PA-VM> show user ip-user-mapping ip 10.20.1.11
    9.4

    Group mapping

    Write policy for groups, not people, and let the directory manage who is in them.

    1. Create an LDAP server profile at : where the directory is, and where and how to search it. (You built one in Lab 3 for administrator logins; the same kind of profile serves here.)
    2. At , select the server profile. The user and group object classes and attributes fill in based on the server type.
    3. Choose the primary username attribute (such as sAMAccountName) and up to three alternates, so names from different mapping sources line up.
    4. Use the Group Include List to send only the groups you need. Only included groups appear in policy drop-downs, which keeps rule editing manageable in a directory with thousands of groups.
    5. Optionally define custom groups from LDAP filters, for example all users whose department attribute is Finance, and give them a name to use in policy.

    Think of it this way

    A rule naming 30 marketing employees is a seating chart that's wrong the day someone is hired. A rule naming the marketing group is a sign on the door that says "Marketing." HR changes who is in the group; the sign never changes.

    9.5

    Users and groups in Security policy

    The Source tab's Source User field, and what each choice means.

    • any: every user, mapped or not.
    • known-user: any user the firewall has mapped. Useful to require identification without naming who.
    • unknown: traffic from addresses with no mapping, such as servers, printers, or unidentified devices.
    • pre-logon: GlobalProtect clients connected before the user has logged in to the machine.
    • select: specific users and groups.

    Dynamic user groups

    A dynamic user group contains every username carrying a matching tag. Like dynamic address groups (Module 6), membership changes take effect without a commit, and DUGs work in Security, Authentication, and Decryption policy. Two typical uses: a security tool tags a user whose account shows risky behavior, moving them into a restricted DUG within seconds; or a time-limited tag grants a contractor access that expires on its own.

      Why an explicit deny rule?

      Lab 11 ends its rulebase for the Acquisition zone with Deny-All-Others, even though interzone-default would deny unlisted traffic anyway.       The lab at a glance

      What you build. The Acquisition zone and the two application groups already exist in the starting configuration.

      1. Every lab starts the same way. On the client desktop, open Firefox to https://192.168.1.254, log in with the credentials in your lab guide, then go to and click Load named configuration snapshot.       2. Review the existing configuration: the Acquisition-Allow-All rule and the Allowed-Corp-Apps and Allowed-Mktg-Apps application groups. Clear the hit counters on all rules.
      3. Generate traffic: in Remmina, connect to the Server-Extranet host and run the Appgenerator-2.sh script from the directory in the guide. Watch the Traffic log fill with traffic hitting Acquisition-Allow-All, and add the Source User column.
      4. Enable User Identification on the Acquisition zone at .
      5. Rewrite the policy: rename Acquisition-Allow-All to Allow-Corp-Apps and limit it to the Allowed-Corp-Apps group; add Allow-Mktg-Apps (source user marketing, Allowed-Mktg-Apps, dependencies added to the rule); add Deny-All-Others at the bottom for the Acquisition zone. Commit.
      6. Verify User-ID: run the script again, check , and in the firewall CLI run show user ip-user-mapping all.
      7. Answer the guide's questions with Traffic log filters: which rule handles youtube-base, dns, and facebook-base, and which users may use social media.

      Watch out for

      • The high-level steps skip a step. Enabling User Identification on the Acquisition zone appears only in the detailed steps (Task 2.4). Do it whichever version you follow. Without it, policy can't see users, the Source User column stays empty, and the marketing rule never matches.
      • No mappings yet? Mappings appear while the traffic script runs. If the User-ID log is empty, run Appgenerator-2.sh again, as the guide suggests.
      • Rule order. Deny-All-Others must be last. Above Allow-Mktg-Apps it would shadow it, and the commit would warn you.
      • Why a deny rule if interzone-default already denies? Deny-All-Others makes the intent explicit, logs by default, and because its destination zone is any, it also catches traffic that interzone-default would never see (Section 9.5).
      • Use the group, not individual users. Source user marketing is a group. When someone joins marketing in the directory, they get access with no firewall change.

      Summary and self-check

      • User-ID maps IP addresses to users (user mapping) and users to LDAP groups (group mapping), so policy, logs, and reports can use names.
      • Components: the firewall, the PAN-OS integrated agent, the Windows-based agent (sends only mappings, good for remote sites), and the Terminal Services agent (maps port ranges on shared hosts).
      • Mapping methods include server monitoring, session monitoring, client probing, GlobalProtect, syslog listening, Authentication Portal, the Terminal Services agent, XML API, and XFF headers. Combine them to cover every population.
      • Enable User-ID on internal source zones only. Configure monitored servers and a least-privilege service account at Device > User Identification > User Mapping, then verify Connected status and mappings.
      • Group mapping uses an LDAP server profile, a primary username attribute, an include list, and optional custom groups.
      • Source user can be any, known-user, unknown, pre-logon, or specific users and groups. Dynamic user groups change membership by tag without a commit.

      Key terms

      User-ID, user mapping, group mapping, User-ID agent, Terminal Services agent, server monitoring, Authentication Portal, GlobalProtect, known-user, dynamic user group.
