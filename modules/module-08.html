Application Identity (App-ID)

So far your rules have allowed any application, as long as the zones matched. That is a port-based firewall wearing a next-generation badge. This module teaches App-ID properly: how the firewall names traffic, what its labels mean when it can't, and how to move a rulebase from ports to applications without breaking the business.

    Part A

    How App-ID works

    Naming traffic by what it is, not by the port it uses.

    8.1

    What App-ID does

    An application, to the firewall, is anything whose traffic can be labeled, monitored, and controlled.

    That definition is broader than "program." Gmail, Google Docs, and Google Calendar are separate applications even though they come from one company and one browser. Slack, Netflix, and Zoom are applications. So are DNS, SSH, and the update service the firewall itself uses. Each has an entry in the App-ID database at , with its category, subcategory, technology, a risk rating from 1 to 5, characteristics such as "evasive" or "tunnels other applications," its standard ports, and the applications it depends on. Palo Alto Networks also publishes the database online as Applipedia.

    How identification works

    App-ID runs on every session and tries, in order:

    1. Application signatures: patterns in the traffic that match a known application.
    2. Decryption, if the traffic is encrypted and a Decryption policy rule says to decrypt it (Module 13), so the signatures can see inside.
    3. Protocol decoders: understanding a protocol such as HTTP well enough to find the application riding inside it.
    4. Behavioral heuristics: recognizing applications that deliberately avoid signatures, such as some peer-to-peer and proxy tools.

    If none of these match, the traffic is labeled unknown. Whatever the result, App-ID keeps watching the session, because the application can change partway through (Section 8.3).

    Why it beats port-based rules

    A port-based rule that allows udp/53 for DNS allows anything on udp/53. BitTorrent configured to use port 53 sails through, and the logs say "port 53 allowed." An application-based rule that allows dns checks the traffic itself: DNS passes, BitTorrent on port 53 is identified as bittorrent and denied, and the logs say so.

    The difference is starker for brand-new threats. A traditional intrusion prevention system is a negative model: it blocks what it has a signature for, so a zero-day command-and-control channel with no signature yet is allowed. App-ID policy is a positive model: you list what to allow. The zero-day channel is not DNS, not web-browsing, not anything you allowed, so it is denied even though nobody has seen it before.

    Think of it this way

    A blocklist at a club door turns away people whose photos are on file. A guest list lets in only people whose names are on it. App-ID policy is a guest list. A stranger with no photo on file still doesn't get in.

    8.2

    Labels for traffic App-ID can't name

    The Traffic log's Application column sometimes shows something that isn't an application. Each of those labels tells you exactly how far the session got.

    TCP

    TCP gives App-ID a sequence to watch: SYN, SYN-ACK, ACK, then data.

    LabelWhat happened
    not-applicableSecurity policy dropped the traffic before App-ID identified it, for example on the zone-and-port pre-check.
    incompleteThe three-way handshake never completed, or it completed and then no data was sent.
    insufficient-dataSome payload arrived, but not enough to identify anything.
    unknown-tcpPlenty of data, but nothing matched.
    unknown-p2pUnidentified traffic that behaves like peer-to-peer.

    UDP

    UDP has no handshake; App-ID starts on the first packet, which already carries data. So the labels are simpler: not-applicable if policy dropped it first, unknown-udp for unidentified UDP, and unknown-p2p for peer-to-peer behavior.

    In the field

    A burst of incomplete sessions to many ports from one source is a scan: the scanner sends SYNs and never finishes. insufficient-data is usually harmless noise. unknown-tcp and unknown-udp that you are allowing deserve a look every time (Section 8.5).

    8.3

    Shifts, dependencies, and implicit applications

    Applications are layered and they change mid-session. Policy has to account for both.

    Application shifts

    Many sessions start as one application and become another. A browser connects to a site and App-ID first sees web-browsing; as the page loads it recognizes the site's own application (generic-app-base, say); when the user opens the site's chat window it shifts again to generic-app-chat. Each time the application changes, the firewall checks Security policy again with the new application. A rule that allows the base application but not the chat function lets the page load and blocks the chat.

    Dependencies

    Some applications need others to work. Office on demand, for example, depends on ms-office365-base and sharepoint-online. If a rule allows office-on-demand but no rule allows its dependencies, the application half-works and users call the help desk. Two places help:

    • Before writing the rule, look at the application in ; its Depends On list shows what else must be allowed. When you add an application to a rule, the rule dialog offers its dependencies too.
    • After writing it, read the commit results. A commit checks whether every application's dependencies are allowed by some rule and reports unresolved dependencies per rule, with links to fix them.

    Implicitly allowed applications

    Many applications are built on others and allow them implicitly. facebook-base, for instance, implicitly allows the web-browsing and ssl it starts as, so you don't add those to the rule. The application's entry lists what it implicitly uses.

    Common misconception

    "If I allow facebook-base I've allowed all of Facebook." Facebook's chat, posting, file-sharing, and other functions are separate applications. That granularity is the point: you can allow reading while blocking posting.

    8.4

    Application groups, filters, and tags

    Thousands of applications, one readable rulebase.

    • An application group, at , is a static list you maintain: for example, paloalto-apps for the firewall's own services, or Allowed-Corp-Apps for approved business tools.
    • An application filter, at , is dynamic. You choose attributes (category, subcategory, technology, risk, characteristics, or tags) and every matching application is included. When a content update adds a new App-ID that matches, it joins the filter automatically. A filter such as "file-sharing, risk 4 or 5" stays current without you touching it.
    • Groups can contain filters, and both can be used in Security, QoS, and Policy-Based Forwarding rules.

    Palo Alto Networks also assigns predefined tags to applications, updated with content (such as Enterprise VoIP or Web App), and you can add custom tags. Tags become filter criteria, so "everything tagged Enterprise VoIP" is one object.

    Positive enforcement in practice

    Write rules that say what to allow, by application, group, or filter, rather than by port. Leave service as application-default. Let interzone-default (or your own deny rule) catch everything else. When a web-based application is blocked, the Application Block Page, enabled at , tells the user why, instead of leaving them with a page that silently fails to load.

    8.5

    Unknown and encrypted traffic

    What to do when App-ID can't see, or can't see in.

    Unknown applications

    Allowed traffic labeled unknown-tcp, unknown-udp, or unknown-p2p is a gap in your visibility, and attackers like gaps. Check the Traffic log for it regularly. If it is really HTTP or HTTPS, App-ID would have called it web-browsing or ssl, so unknown means something genuinely unrecognized. Your options:

    • Block it. A rule denying unknown-tcp, unknown-udp, and unknown-p2p is a strong default, but it can block more than intended, such as an in-house application nobody told you about. Watch the logs after enabling it.
    • Write a custom application with your own signature at , so a known internal application gets a real name and can be allowed specifically.
    • Use an Application Override policy at to label traffic on a given port and address as a custom application. Use this sparingly: overridden traffic skips App-ID's normal identification and is not inspected for threats.
    • Ask Palo Alto Networks for a new App-ID if the application is commercial and common.

    Encrypted traffic

    Without decryption, App-ID still gets clues from TLS: the server name a client requests (SNI), and the name in the server's certificate. That is often enough to tell twitter from facebook. But when many sites share one address and certificate, and to see anything about what happens inside the session, the firewall must decrypt (Module 13). Then App-ID applies its full set of signatures, decoders, and heuristics to the decrypted traffic.

    application-default understands encryption for a handful of applications (web-browsing, smtp, ftp, ldap, pop3, and imap): it matches each on its standard cleartext port and, once decrypted, on its secure port.

    Non-standard ports

    Because App-ID ignores the port when identifying, you can write rules that use it deliberately: block ssh tunnels on any port, allow ms-rdp only on application-default, or allow mysql only on the one non-standard port your database team uses, by naming a custom service.

    Exam tip

    "Traffic was identified as unknown-tcp" and "traffic was labeled incomplete" mean very different things. Unknown means data flowed and nothing matched. Incomplete means App-ID never had data to look at.

    8.6

    Migrating to App-ID rules, and keeping App-ID current

    Most firewalls inherit port-based rules. Policy Optimizer turns them into application rules using what the firewall has actually seen.

    Three phases

    1. Migrate the legacy rules as they are. Bring the old firewall's port-based policy onto the new firewall, test, cut over, and let it run while the firewall logs which applications each rule really carries. (Palo Alto Networks' Expedition tool can automate parts of this.)
    2. Add application-based rules above the port-based ones. At , any rule whose application is any is listed. Its Apps Seen count and Compare view show which applications matched it. Use that list to build application rules, highest-value rules first: those passing the most data, the most sessions, the most applications, and the most stable traffic.
    3. Remove the port-based rules. After about 60 days, check their hit counts. Disable rules with no new hits (disabled rules appear in gray italics; tag them if you like), and delete them after about 90 days.

    Four ways to convert a rule

    OptionWhat it doesWhen to use it
    Create Cloned RuleCopies the rule with only the applications you select, placed above the original. Prompts for dependencies.The safest choice, especially when the rule carries many applications.
    Add to This RuleReplaces the port-based rule's any with the applications you select.Riskier: any legitimate application you forget stops working.
    Add to Existing RuleAdds the applications to another rule that already exists.When an application rule for that traffic already exists.
    Match UsageCopies every application in Apps Seen into the rule.Only when the rule matches a small number of applications, all legitimate.

    Whichever you choose, set the converted rule's service to application-default yourself; Policy Optimizer leaves it as it was.

    Keeping App-ID current

    New App-IDs arrive in Applications and Threats content updates (Module 2). A new App-ID can change how existing traffic is labeled: something your rule allowed as ssl might now be identified as a specific application your rule doesn't list. To avoid surprises, review the new and modified App-IDs in each content release before installing it, and consider installing with new App-IDs disabled, checking their policy impact, and then enabling them.

    Watch out for

    • Why the firewall's own traffic hits a Security rule. In this lab the management interface (192.168.1.254) uses the vRouter as its gateway, and the vRouter sends internet traffic back through ethernet1/2. So the firewall's update traffic arrives on Users_Net like any user's and is matched by Security policy. That is a lab shortcut; in production the management network has its own path (Section 2.4).
    • The shadow is the lesson. Users_to_Internet allows any application, so it matches the update traffic before Allow-PANW-Apps can. Narrowing it is what fixes the problem; moving rules around is not what the lab asks for.
    • Dependencies. When you add applications like dropbox or ms-office365, PAN-OS offers their dependencies. Add them to the current rule, or the commit will report unresolved dependencies and the applications will half-work.
    • The Application Block Page shows only for web-based applications. Without it, a blocked site simply fails to load, which looks like a network problem to the user.
    • Answer the questions. The guide asks you to decide which applications should and should not be allowed. Write your answers down; they are the part of this lab that is about judgment, not clicking.

    Summary and self-check

    • App-ID identifies applications with signatures, decryption where policy allows, protocol decoders, and heuristics, regardless of port, and keeps watching for shifts.
    • Application-based rules are a positive model: anything not listed, including never-seen threats, is denied.
    • Labels: not-applicable (dropped before identification), incomplete (no completed handshake or no data), insufficient-data (too little data), unknown-tcp/udp/p2p (data, no match).
    • Policy is re-checked on every application shift. Dependencies must be allowed by some rule and are reported at commit. Some applications implicitly allow their parents.
    • Application groups are static; application filters are dynamic and pick up new App-IDs. Tags can drive filters. Enable the Application Block Page for blocked web applications.
    • Investigate allowed unknown traffic: block it, write a custom application, or use Application Override sparingly. Encrypted traffic needs decryption for full identification.
    • Migrate with Policy Optimizer in three phases. Create Cloned Rule is safest; set application-default after converting. Review new App-IDs before installing content.
