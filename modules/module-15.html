SASE Overview and Architecture

For fourteen modules the perimeter has been a box at the edge of the network. But users now work from anywhere, and most of their applications live in the cloud. Secure Access Service Edge moves the firewall's inspection into the cloud, close to wherever users are. This module explains the idea in vendor-neutral terms, then shows how Palo Alto Networks builds it with Prisma Access.

    Part A

    SASE in general

    The problem, the idea, and the building blocks, in any vendor's terms.

    15.1

    Why the perimeter moved

    The classic design assumes users and applications are inside. Increasingly, neither is.

    Everything in this course so far fits a familiar picture: a firewall at headquarters inspects traffic between the internal network and the internet. Branch offices send their traffic back to headquarters over MPLS circuits or VPN tunnels so that it passes the same firewall. Remote employees connect a VPN to headquarters for the same reason. That design is called hub-and-spoke, and it worked when applications lived in the headquarters data center.

    Three changes strain it:

    • Applications moved to the cloud. Email, file storage, CRM, and collaboration are SaaS services on the internet. A branch user's traffic to Microsoft 365 travels to headquarters, out to the internet, and back the same way: the hairpin, or trombone.
    • Users left the building. Hybrid and remote work put most users outside the network most of the time. VPN concentrators sized for a few travelers become bottlenecks for everyone, and users who disconnect the VPN to "make it faster" have no protection at all.
    • The VPN model grants too much. Once connected, a VPN user is on the network and can often reach far more than their job needs, which is exactly the lateral-movement problem Zero Trust addresses (Module 1).

    Think of it this way

    Hub-and-spoke security is a single airport security checkpoint for an entire country: every traveler must fly to the capital to be screened before going anywhere, even next door. SASE puts a checkpoint in every city.

      15.2

      SASE and SSE defined

      Networking and security, converged and delivered from the cloud.

      Secure Access Service Edge (SASE), a term introduced by the analyst firm Gartner in 2019, describes delivering wide-area networking and network security together as a cloud service, from points of presence close to users, with policy based on identity rather than location. Gartner later named the security half on its own: Security Service Edge (SSE). SASE = SD-WAN + SSE.

      Building blockWhat it doesWhere you've seen it
      SD-WANConnects sites over any mix of links, steering each application over the best pathReplaces the MPLS backhaul in Simulation 15.1
      Firewall as a Service (FWaaS)Next-generation firewall inspection in the cloudEverything in Modules 6 to 13
      Secure Web Gateway (SWG)Filters and inspects web trafficURL Filtering, threat profiles, decryption (Modules 10, 11, 13)
      Zero Trust Network Access (ZTNA)Per-application access to private apps after verifying identity and deviceUser-ID and least-privilege rules (Modules 6, 9), extended to remote users
      Cloud Access Security Broker (CASB)Visibility and control over SaaS applications and the data in themApp-ID for SaaS (Module 8), Data Filtering (Module 10), and Module 16

      Many SASE offerings also include data loss prevention, DNS security, remote browser isolation, and digital experience monitoring. A single-vendor SASE provides everything in one platform with one policy; a multi-vendor design combines, say, one company's SD-WAN with another's SSE.

      Common misconception

      "SASE replaces the firewall." It moves firewall functions to where users are. Data centers, factories, and campuses still have on-premises NGFWs, and most organizations run both, ideally with one policy model across them.

      15.3

      ZTNA versus VPN

      Access to an application, not to a network.

      Traditional remote-access VPNZTNA
      What the user getsA connection to the networkA connection to specific applications
      TrustVerified once at connect, then implicitIdentity and device posture checked per application, and rechecked
      Visibility of other resourcesOften reachable and discoverableHidden; unauthorized apps aren't even reachable
      Lateral movement after a compromisePossible across what the network allowsLimited to the apps that user is granted
      Inbound exposureVPN gateway listens on the internetOften outbound-only connectors from the app's location to the cloud

      You've already built the ingredients on the firewall: User-ID ties traffic to people (Module 9), App-ID names the applications (Module 8), and Security rules allow specific applications to specific groups (Module 6). ZTNA applies the same least-privilege thinking to remote users and private applications, with device posture as an extra condition.

      15.4

      Prisma Access architecture

      The firewall you've learned, run by Palo Alto Networks in cloud locations around the world.

      Prisma Access is Palo Alto Networks' SASE platform. Palo Alto Networks deploys and operates the security infrastructure globally; you choose locations and write the policy. Its security processing nodes inspect traffic with the same App-ID, User-ID, and Content-ID engines you've used all semester, so a Security rule, a URL Filtering profile, or an antivirus profile means the same thing in Prisma Access as on the lab firewall.

      Three ways in

      Connection typeWho or what it servesHow it connects
      Mobile UsersRemote and traveling usersAn agent on the device connects to the nearest Mobile User security processing node (MU-SPN). Historically this agent was GlobalProtect (Module 9); Palo Alto Networks is moving customers to its newer Prisma Access Agent. Users can also connect through an explicit proxy, with or without an agent, including Palo Alto Networks' enterprise browser.
      Remote NetworksBranch offices and the users in themAn IPsec tunnel from the branch's router, firewall, or SD-WAN device to a Remote Network security processing node (RN-SPN).
      Service ConnectionsHeadquarters and data centersIPsec tunnels to corporate access nodes, so mobile users and branches can reach internal resources, and reach each other.

      For private applications, a ZTNA Connector deployed near the application makes an outbound connection to Prisma Access, so users reach the app through the service without any inbound VPN to the data center.

      Running it

      • Management: through Panorama with the Prisma Access plugin, or through Strata Cloud Manager, Palo Alto Networks' cloud management console, which can manage NGFWs and Prisma Access together.
      • Logging: Prisma Access sends its logs to Strata Logging Service (Module 14), where the familiar log types appear.
      • Identity: users authenticate through SAML or other identity providers, often via the Cloud Identity Engine, which also supplies group information for policy, the cloud counterpart of group mapping (Module 9).

      Names change; concepts don't

      Product names in this space change often. GlobalProtect is giving way to the Prisma Access Agent (newer documentation calls it simply Prisma Agent), and the enterprise browser has been renamed more than once. Check current documentation for names. The architecture of agents and branches connecting to cloud processing nodes, with the same NGFW policy model, is what to remember.

      15.5

      Choosing a design

      On-premises, cloud-delivered, or both.

      FactorFavors on-premises NGFWFavors cloud-delivered (SASE)
      Where users areMostly on siteRemote, hybrid, or many small sites
      Where apps areData center, local systems, operational technologySaaS and public cloud
      Traffic volume per siteVery high, such as a data center or campus coreModest, spread across many locations
      OperationsStaff to run appliances, upgrades, and capacity planningPrefers the provider to run infrastructure and scale it
      Data location rulesStrict requirements that traffic stay on premisesProvider locations satisfy the requirements

      Most real designs are hybrid: NGFWs protect the data center and segment internal zones, while Prisma Access secures remote users and small branches, all managed with one policy model. The skills from this course carry across both: the same zones, rules, App-ID, User-ID, profiles, decryption, and logs.

      Summary and self-check

      • Hub-and-spoke security backhauls branch and remote traffic to headquarters, causing the SaaS hairpin, VPN bottlenecks, and broad network access.
      • SASE converges SD-WAN and security (SSE) in cloud points of presence close to users, with identity-based policy. SSE's building blocks include SWG, CASB, ZTNA, and FWaaS.
      • ZTNA grants per-application access with continuing identity and posture checks; a VPN grants network access after one check.
      • Prisma Access connects mobile users (agent or explicit proxy to MU-SPNs), remote networks (IPsec to RN-SPNs), and service connections (to corporate access nodes), plus ZTNA Connectors for private apps. It's managed by Panorama or Strata Cloud Manager and logs to Strata Logging Service.
      • Its inspection is the NGFW you've learned. Most organizations run a hybrid of on-premises NGFWs and cloud-delivered security.

      Key terms

      SASE, SSE, SD-WAN, FWaaS, SWG, ZTNA, CASB, Prisma Access, security processing node, service connection.
