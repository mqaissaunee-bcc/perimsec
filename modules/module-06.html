Zones lock every door. Security policy decides which doors open, for whom, and for which applications. This module follows a packet through the firewall, then teaches you to write, order, test, and maintain the rules it meets along the way.

    Part A

    How policy is evaluated

    The path a packet takes, and the logic that decides which rule it meets.

    6.1

    Following a packet through the firewall

    Almost every "why didn't my rule work?" question is answered by knowing the order in which the firewall does things.

    When a packet arrives, the firewall first asks whether it belongs to a session that already exists. If it does, the packet takes the fast path: everything decided when the session was created still applies, and it moves straight to inspection and forwarding. If not, the firewall runs session setup, the slow path:

    1. Source zone: the zone of the interface the packet arrived on. Zone Protection and DoS Protection can drop it here.
    2. Forwarding lookup: Policy-Based Forwarding if a rule matches, otherwise the virtual router's route lookup. The egress interface gives the destination zone.
    3. NAT policy lookup: the firewall decides what translation, if any, applies. With destination NAT it routes the translated address to find the post-NAT destination zone.
    4. Security policy pre-check: a first match on zones, addresses, users, and service (port). The application is not known yet, so this check ignores App-ID.
    5. Session created, with a session ID.

    Then, for new and existing sessions alike, inspection and enforcement:

    1. App-ID identifies the application as data arrives, and keeps watching for application shifts.
    2. Security policy is checked again with the application.
    3. If the traffic is encrypted and a Decryption policy rule matches, it is decrypted.
    4. Content-ID applies the Security Profiles attached to the matching rule.
    5. The packet is re-encrypted if needed, NAT is applied, and it is forwarded.

    Exam tip

    Two facts from this flow appear on almost every firewall exam. Security policy uses the pre-NAT IP addresses. The destination zone in a Security policy rule is the post-NAT zone. Module 7 works through why.

      6.2

      Sessions, match criteria, and rule types

      What a rule actually matches, and which way it points.

      Sessions and flows

      Every packet is matched to a session, and every session is matched to one Security policy rule. A TCP session has two flows: client-to-server and server-to-client. The firewall's idea of "client" and "server" is simply who started the conversation: the initiator is the client, the responder is the server, whatever services they run.

      A rule allows the client-to-server direction. Return traffic in the server-to-client flow is part of the same session and is allowed automatically. You never write a rule for the reply.

      Match criteria

      Source and destination zone are the basic criteria. Rules can be made more precise with source and destination address, source user, device or HIP profile, application, service (port), and URL category. A session matches a rule only if it matches every field.

      Rule types

      • Universal (the default): matches both interzone and intrazone traffic for the zones listed. A universal rule from ZoneA and ZoneB to ZoneA and ZoneB covers A to A, A to B, B to A, and B to B.
      • Intrazone: only traffic within the same zone. You choose source zones; the destination is the same zone automatically.
      • Interzone: only traffic between different zones in the lists.

      The two default rules

      At the bottom of every rulebase sit two predefined rules: intrazone-default (allow) and interzone-default (deny). Unlike your own rules, they do not log by default. You can't delete or move them, but you can override them to enable logging, which is very useful while troubleshooting ("why is this traffic being dropped?"). You can also change their action or attach Security Profiles to intrazone-default.

      In the field

      Enable logging on interzone-default. Without it, traffic that no rule allows disappears without a trace, and you lose the evidence you need to write the rule that's missing.

      6.3

      Rule order, shadowing, and hit counts

      The firewall stops at the first rule that matches. Everything about rule design follows from that.

      Rules are evaluated from top to bottom. The first rule whose criteria all match decides the session; rules below it are never consulted. Two consequences:

      • Put specific rules above general ones. A rule that blocks SSH to the extranet must sit above a rule that allows all applications to the extranet.
      • Combine rules where you can. Two rules that differ only in source zone, Inside to Outside and Guest to Outside with the same applications, can usually become one rule with both zones in the source.

      Shadowing

      Rule shadowing happens when an earlier rule matches every session a later rule would. The later rule can never be hit; it is in the earlier rule's shadow. Shadowing is usually a mistake, and a dangerous one when the shadowed rule is a block rule. The commit reports it: the Commit Status window has a Shadowed Rule list where you can click through to the rule causing the shadow and the rule shadowed. Fix it by reordering or by making the earlier rule more specific.

      Hit counts and unused rules

      The Security policy table can show, for each rule, how many sessions it has matched, when it was first and last hit, and how many applications it has seen. Use it to verify that a new rule is actually catching traffic, and to find rules that are never used. Unused rules are highlighted in the rule table, and filters rules unused over a period you choose. Removing them shrinks the attack surface and makes the rulebase easier to reason about. Hit counts and unused-rule tracking reset when the data plane restarts, so check the time span before deleting anything.

        Part B

        Building and maintaining rules

        The rule dialog tab by tab, and the objects and tools that keep a rulebase readable.

        6.4

        Building a Security policy rule

        A tour of , one tab at a time.

        • General: a name, rule type (universal, intrazone, interzone), description, and tags. An audit comment records why the rule was added or changed; the Audit Comment Archive shows the comment history alongside the configuration logs, and lets you compare versions of the rule.
        • Source: zones, addresses (objects, groups, external dynamic lists, or geographic regions), users, and devices. Negate inverts the address match: the rule matches every address except those listed.
        • Destination: zones, addresses, and devices, with the same Negate option.
        • Application: the default is any. Add specific applications instead, and check their dependencies (Module 8). A commit reports dependencies that no rule satisfies.
        • Service/URL Category: the service defaults to application-default, which allows each application only on its standard ports. You can choose any, a specific service, or one you create at . The only predefined services are service-http and service-https. URL categories (Module 11) can also be match criteria here.
        • Actions: the action (allow, deny, drop, reset client, reset server, reset both), the Security Profiles to attach (Module 10), logging at session start and/or session end, a log forwarding profile, and an optional schedule. With drop and the reset actions you can also send an ICMP unreachable to the client.

        Logging at session end is the default and the recommendation, because the end-of-session entry has the final application, byte counts, and the reason the session ended. Add log at session start temporarily when troubleshooting sessions that never seem to end.

        Schedules

        A schedule, created at , limits when a rule is active: daily, on certain days of the week, or on specific calendar dates, using 24-hour time. Attach it on the Actions tab, for example to allow streaming video only at lunch.

        Common misconception

        "Service any is the safest choice so nothing breaks." Service any allows an approved application on every port, which is exactly how evasive applications and attackers slip through. Use application-default unless an application genuinely needs a non-standard port, and then name that port in a custom service.

        6.5

        Objects, groups, and tags

        Name things once, use them everywhere, and change them in one place.

        Address objects

        An address object, at , gives a name to an IP address, a subnet (IP netmask), an IP range, an IP wildcard mask, or an FQDN. A rule that reads "Extranet-Web-Server" is easier to review than one that reads 192.168.50.80, and when the server moves you change the object, not every rule.

        Address groups

        • A static address group lists address objects and other groups. Membership changes by hand and needs a commit.
        • A dynamic address group includes any IP address carrying a matching tag. Tags can come from external systems through the API or from the firewall's own log-based auto-tagging, and membership changes take effect without a commit. A classic use: when a host triggers a threat alert, tag it "Quarantine," and a rule that blocks the Quarantine group isolates it immediately.

        For lists of addresses maintained outside the firewall, such as threat-intelligence feeds of known-bad IPs, use an external dynamic list. PAN-OS includes predefined lists maintained by Palo Alto Networks, such as known malicious, high-risk, and bulletproof hosting IP addresses, which you can use directly as source or destination addresses. Lab 5 builds block rules from them.

        Tags

        Tags, created at , label rules and objects with a name and a color. Rules and objects can carry several tags. Use them to filter the rulebase, to spot related rules by color, and to view the rulebase as tag-based groups, where you can move or operate on a whole group of rules at once while rule priority is preserved.

        6.6

        Testing and troubleshooting policy

        Ask the firewall which rule would match before users find out the hard way.

        • Test Policy Match (from the Security policy page, or ) takes a source and destination zone and address, protocol, port, application, and user, and tells you which rule would match. It is the fastest way to check a change or answer "would this be allowed?"
        • Global Find searches the configuration for a string, such as an address or application, and links to every rule and object that uses it.
        • The Traffic log at shows, for each session, the rule that matched, the application, and the session end reason. If traffic is being denied by a default rule, enable logging on that rule and look here.
        • The rule's Usage tab shows its hit count, applications seen, traffic over the past 30 days, and when it was created and last modified.

        The same check is available from the CLI:

        admin@PA-VM> test security-policy-match from Users_Net to Internet source 192.168.1.20 destination 93.184.216.34 protocol 6 destination-port 443 application ssl

        Guided problem 6.1

        The rule that never matches

        You added a rule allowing Users_Net to reach the extranet server with ssh. Users still can't connect, and the rule's hit count stays at zero. Work out what to check, in order.

        1. Zero hits means sessions are matching some other rule first, or never reaching policy. Start with Test Policy Match using the real source, destination, port, and application.
        2. If Test Policy Match names a different rule above yours, you have a shadowing or ordering problem. The commit's shadow list may already have warned you. Move your rule up or narrow the other rule.
        3. If it names interzone-default, one of your rule's fields doesn't match. Compare each field: zones, addresses, application, and service. A custom service with the wrong port, or a destination zone that doesn't match the route, are common culprits.
        4. If Test Policy Match names your rule but users still fail, check the Traffic log for the session end reason, then check routing and NAT. The rule is fine; the problem is elsewhere.

        • The last ping still fails, and that's expected.         Summary and self-check

        • New sessions go through setup: source zone, forwarding lookup (destination zone), NAT lookup, a security pre-check without App-ID, and session creation. Existing sessions take the fast path. Then App-ID, policy with the application, decryption, Content-ID, and forwarding.
        • Security policy uses pre-NAT addresses and the post-NAT destination zone.
        • A session has two flows. Rules allow the initiator's direction; replies are allowed automatically.
        • Rule types are universal (default), intrazone, and interzone. intrazone-default allows and interzone-default denies; neither logs until you override it.
        • Rules are evaluated top-down and the first match wins. Place specific rules above general ones. Shadowed rules are reported at commit. Hit counts and Policy Optimizer reveal unused rules.
        • Prefer specific applications and application-default over any. Log at session end. Schedules limit when rules apply.
        • Address objects, static and dynamic address groups, external dynamic lists, and tags keep policy readable and responsive. Test Policy Match, Global Find, the Traffic log, and the Usage tab are your troubleshooting tools.

        Session, Security policy rule, universal rule, intrazone, interzone, rule shadowing, application-default, address object, dynamic address group, external dynamic list, tag, Traffic log, Policy Optimizer.
