Firewall Administrator Accounts

Shared admin passwords are how small mistakes become untraceable ones. This module gives every administrator their own account, the least privilege they need, and a login checked against the directory your organization already trusts.

    Part A

    Who are you, and what may you do?

    The two questions behind every administrator login.

    4.1

    Authentication and authorization

    Two words that sound alike and do very different jobs.

    • Authentication answers who are you? The firewall checks credentials: a password, a certificate, a second factor.
    • Authorization answers what may you do? For administrators, that is decided by the role assigned to the account.

    A login has to pass both. Good credentials with no role assigned is still a failed login.

    To the firewall, and through it

    The firewall authenticates two very different groups of people:

    • Connecting to the firewall: administrators reaching the web interface, CLI (SSH, Telnet, or console), or XML API. These connections always require authentication. That is this module.
    • Connecting through the firewall: users reaching websites, SaaS apps, or internal servers. The firewall can require these users to authenticate, using an Authentication policy, and then authorizes their access with Security policy built on User-ID (Module 9).

    Both groups can share the same back-end services, such as LDAP or RADIUS. Every administrator action is recorded in the Configuration and System logs, which is why each person needs their own account.

    4.2

    Administrator roles

    Authorization for administrators comes from one of two kinds of role.

    Dynamic roles

    Dynamic roles are built in. You pick one when you create the administrator at :

    • Superuser: full access, including creating other administrators.
    • Superuser (read-only): can see everything, change nothing.
    • Device administrator: full access except managing administrators and roles.
    • Device administrator (read-only): read access to everything except administrator accounts and roles.
    • Virtual system administrator and its read-only variant: limited to specific virtual systems on firewalls that use them.

    Their key property is in the name: when a PAN-OS release adds a feature, dynamic roles update automatically to include it. You never have to maintain them.

    Role-based roles (Admin Role Profiles)

    When the built-in roles are too broad, create an Admin Role Profile at . For each area of the web interface you choose Enable, Read Only, or Disable, and you separately control XML API, REST API, and CLI access. A typical example is a SOC analyst profile that can read logs and the ACC but cannot touch policy.

    The trade-off: custom profiles do not update themselves. After an upgrade adds new features, review your profiles to decide whether each role should have them.

    Exam tip

    "Updated automatically when new features are added" describes dynamic roles. "Granular, per-feature permissions" describes Admin Role Profiles. Expect a question that hinges on that difference.

    Part B

    Where accounts live

    Local accounts, external directories, and certificates.

    4.3

    Local administrator accounts

    Accounts whose credentials are stored on the firewall itself.

    PAN-OS offers two local options:

    1. A local administrator with its own password. At , enter a name and password and choose a role. The password lives in the firewall configuration. The predefined admin account is this kind.
    2. A user in the local user database. Create the user at . You can type a cleartext password or paste an existing password hash. These users can be firewall administrators and can also authenticate users passing through the firewall.

    To use a local database user as an administrator, create an authentication profile at with the type Local Database. On its Advanced tab, two settings matter:

    • Allow List: the users or groups this profile may authenticate. An empty allow list authenticates no one; all allows every user in the database.
    • Account Lockout: the number of failed attempts before lockout and how long the lockout lasts.

    Finally, create the administrator at Device > Administrators with the same username, select the authentication profile, and choose a role.

    In the field

    Keep local accounts to a minimum, usually one or two break-glass accounts for when the directory is unreachable. Everyone else should authenticate against your directory, so that disabling someone's account when they leave also removes their firewall access.

    4.4

    External authentication and sequences

    Let the directory check the password, and the firewall check the role.

    PAN-OS supports five external authentication services: LDAP, RADIUS, TACACS+, Kerberos, and SAML. Authentication profiles can also add multi-factor authentication through supported MFA vendors such as Okta, Duo, and PingID.

    Three objects, chained

    1. A server profile at tells the firewall how to reach the service: addresses, ports, and the account it binds with.
    2. An authentication profile at selects the server profile and sets lockout, allow list, and optional MFA.
    3. Optionally, an authentication sequence at lists several authentication profiles in order.

    Then create the administrator at Device > Administrators. For a non-local account, you do not set a password; you select the authentication profile or sequence, and the external service checks the password.

    How a sequence decides

    The firewall tries each profile in order. If the server is unreachable, the account does not exist there, or the password is wrong, it moves on to the next profile. The first profile that authenticates the user wins, and checking stops. Access is denied only if every profile fails. A common sequence is LDAP first, then the local database, so administrators can still log in with a break-glass account if the directory is down.

    Roles without local accounts

    Normally each administrator needs an entry under Device > Administrators that assigns the role. RADIUS, TACACS+, and SAML can do better: the server returns the administrator's role in a vendor-specific attribute. Set that authentication profile under , and any user the server authorizes can log in with the role the server assigns, with no account on the firewall at all. Administrator access is then managed entirely in the directory.

        4.5

        Certificate-based (non-interactive) login

        Replace the password prompt with a certificate the browser presents automatically.

        Password login is interactive: you type something. Certificate-based login is non-interactive: your browser presents a client certificate, and the firewall verifies it. It applies only to the web interface, not the CLI.

        Three pieces make it work:

        1. A user certificate for each administrator, issued by a certificate authority (CA) and installed in their browser.
        2. A certificate profile at that names the CA certificate that signed the client certificates, which certificate field holds the username, and how to check revocation (CRL or OCSP, optional but recommended). It can also block sessions when certificate status is unknown or the check times out.
        3. The certificate profile selected under .

        On the administrator account, select Use only client certificate authentication (Web). The account no longer needs an authentication profile, but it still needs a role: the certificate proves identity, and the role still decides what that identity may do. For the CLI, the closest equivalent is SSH public key authentication, set on the same administrator account.

        What you will do

        Load a baseline configuration, create a local administrator, configure LDAP and RADIUS server profiles and authentication profiles, combine them in an authentication sequence, and create non-local administrator accounts that log in through it.

        Before you start

        Watch out for

        • Usernames must match. For a non-local administrator, the name under Device > Administrators must match the account in LDAP or RADIUS exactly.
        • Allow lists. If a correct password is rejected, open the authentication profile's Advanced tab and check that the user or all is in the allow list.
        • Commit before testing. New profiles and accounts do nothing until committed.
        • Read the System log when a login fails. Filter for authentication events; the entry usually names the profile that failed and why.
        • Keep the admin session open. Test new accounts in a private browser window so you stay logged in as admin to fix mistakes.

        Summary and self-check

        • Authentication verifies identity; authorization decides permissions. Administrator logins need both.
        • Administrators connect to the firewall; users connect through it. The same back-end services can serve both.
        • Dynamic roles are built in and update automatically. Admin Role Profiles give granular web, CLI, XML API, and REST API permissions but need review after upgrades.
        • Local options: an administrator with a password in the configuration, or a local user database account used through a Local Database authentication profile with an allow list and lockout settings.
        • External authentication chains a server profile, an authentication profile, and optionally an authentication sequence, which tries profiles in order and fails only if all fail.
        • RADIUS, TACACS+, and SAML can return the administrator's role, removing the need for local administrator accounts.
        • Certificate-based login uses a certificate profile and works only for the web interface; the account still needs a role.

        Key terms

        Authentication, authorization, dynamic role, Admin Role Profile, local user database, server profile, authentication profile, authentication sequence, certificate profile, RADIUS, TACACS+, SAML, LDAP, MFA.
