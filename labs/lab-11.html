Lab 11: Controlling Access to Network Resources with User-ID

    01

    What this lab is for

    IP addresses change; people and their roles don't. User-ID maps addresses to usernames and usernames to directory groups, so a rule can say "marketing may use these applications" and keep saying it as laptops move between networks.

    The story: your company has acquired another, whose users sit in a new Acquisition zone. Another admin left a rule allowing them any application to anywhere. You'll tighten it in three layers: approved apps for everyone, extra apps for the marketing group, and an explicit deny for the rest.

    • You'll leave with: User-ID enabled on Acquisition, Allow-Corp-Apps (renamed from Acquisition-Allow-All), Allow-Mktg-Apps for the marketing group, and Deny-All-Others at the bottom.
    • Builds on: Module 9. Simulation 9.2 (who gets what) mirrors this lab's results. You'll do this lab in week 5, before Labs 8 to 10, to match the module order.
    • Sets up: the Acquisition-zone rules that Labs 8, 13, and 14 assume.

    Walkthrough of the detailed steps

    2.1Load the lab configuration

    Every lab starts from a known baseline, so your firewall matches the guide no matter what you did last time.

    1. On the client desktop, log in as lab-user, open Firefox, and browse to https://192.168.1.254. Log in as admin with the password from Lab Settings. If the login page does not appear, wait 1 to 3 minutes for the firewall to finish booting and refresh.
    2. Go to and click Load named configuration snapshot. Choose edu-210-11.0a-11.xml and click OK, then Close.
    3. Open Tasks (lower right) and confirm the Load task shows completed.
    4. Click Commit (upper right), then Commit in the dialog, and wait for it to finish.

    Loading is not committing

    A loaded snapshot replaces only the candidate configuration. Until you commit, the firewall is still running whatever was there before, and nothing in the lab will match the guide.

    2.2Examine the firewall configuration

    1. Go to and open Acquisition-Allow-All. Note: source zone Acquisition, destination zone any, application any, action Allow. Click OK.
    2. Click Reset Rule Hit Counter > All rules and confirm.
    3. Go to and look at Allowed-Corp-Apps and Allowed-Mktg-Apps.

    Why "any to any" is the problem

    That rule lets every acquired user reach every zone with every application, including your users' network. It's common after a merger, and it's exactly what User-ID and App-ID together are meant to replace.

    2.3Generate traffic from the Acquisition zone

    1. Open Remmina and double-click Server-Extranet.
    2. Change to the scripts folder and run the generator. Let it finish.
    Commandpaloalto42@extranet1:~$ cd /home/paloalto42/pcaps92019/app.pcaps/
paloalto42@extranet1:~$ ./Appgenerator-2.sh
    1. In , clear filters. Almost everything hits Acquisition-Allow-All. Allow 3 to 6 minutes for logs to appear.
    2. Add the Source User column and drag it between Receive Time and Source.

    The guide describes a different task

    The introduction to 2.3 talks about a data-plane packet capture for a custom application signature. Nothing like that happens: you just run the traffic script.

    Source User is empty for now

    That's expected. The zone doesn't have User-ID turned on yet.

    Screenshot 1 The Traffic log showing Acquisition traffic hitting Acquisition-Allow-All, with an empty Source User column.

    2.4Enable User-ID on the Acquisition zone

    1. Go to and open Acquisition.
    2. Check Enable User Identification and click OK.

    The high-level steps skip this

    It appears only here in the detailed steps. Without it, the firewall never maps users in this zone, the Source User column stays empty, and the marketing rule can never match.

    Screenshot 2 The Acquisition zone with Enable User Identification checked.

    2.5Turn Acquisition-Allow-All into an approved-apps rule

    1. Open Acquisition-Allow-All in .
    2. General: rename it Allow-Corp-Apps, description Allows only approved apps for Acquisition users.
    3. Application: uncheck Any and add the Allowed-Corp-Apps group. Click OK.

    2.6Create the marketing apps rule

    1. Click Add. General: name Allow-Mktg-Apps, description Allows only users of marketing group to access Mktg apps.
    2. Source: zone Acquisition. Under Source User, click Add and enter marketing.
    3. Destination: set the zone drop-down to any.
    4. Application: uncheck Any, add Allowed-Mktg-Apps, then check Depends On and click Add to Current Rule.
    5. Actions: confirm Allow. Click OK.

    A group, not a list of people

    Source user marketing is a directory group. When someone joins marketing in the directory, they get access with no firewall change.

    Screenshot 3 Allow-Mktg-Apps showing source zone Acquisition and source user marketing.

    2.7Create the deny rule

    1. Click Add. Name Deny-All-Others, description Denies non-approved applications for users in Acquisition zone.
    2. Source: zone Acquisition, source user any. Destination: zone any. Application: Any.
    3. Actions: change Action to Deny. Click OK.
    4. Make sure it sits at the bottom, just above intrazone-default. Commit.

    Why deny explicitly if interzone-default already does?

    Deny-All-Others states the intent, logs by default, and, because its destination zone is any, also catches Acquisition-to-Acquisition traffic that intrazone-default would otherwise allow.

    Order matters

    Above Allow-Mktg-Apps, the deny would shadow it. Last is the only correct place.

    Screenshot 4 The rulebase with Allow-Corp-Apps, Allow-Mktg-Apps, and Deny-All-Others in that order.

    2.8Generate traffic again

    1. Back in the Server-Extranet Remmina window, run the script again from the same folder and let it finish. Then close the window.
    Commandpaloalto42@extranet1:~$ ./Appgenerator-2.sh

    2.10Examine the Traffic log

    Apply each filter and read the Rule and Source User columns.

    Log filter( app eq youtube-base )
( app eq dns )
( app eq facebook-base )
( app eq facebook-base ) and ( action eq allow )
( app eq instagram-base ) and ( user.src eq 'chicago\sholmes' )
( app eq instagram-base ) and ( user.src eq 'chicago\bbart' )

    Curly quotes break the filter

    The guide prints the user filters with curly quotes (‘chicago\sholmes’). The filter parser needs straight single quotes, as above. Use the Copy button.

    Q1: Which rule handles youtube-base?

    Read the Rule column. The answer depends on which group youtube-base is in. If it's in Allowed-Corp-Apps, you'll see Allow-Corp-Apps; if only in Allowed-Mktg-Apps, you'll see Allow-Mktg-Apps for marketing users and Deny-All-Others for everyone else. Open the two groups in Objects > Application Groups to confirm.

    Q2: Which rule handles dns?

    You'll likely see two: Allow-Corp-Apps for Acquisition users and Users_to_Internet for the client's own lookups. Check the Source Zone column to tell them apart.

    Q3: Which rules handle facebook-base?

    c and d: Allow-Mktg-Apps and Deny-All-Others. Marketing users are allowed; everyone else in Acquisition is denied.

    Q4 to Q6: Which users get facebook-base and instagram-base?

    The answers are whoever is in the marketing group in the lab directory. The allowed filter (Q4) lists them in Source User. For sholmes and bbart, an allowed entry means Yes; only denied entries (Deny-All-Others) means No.

    06

    How this looks on a real firewall

    • Mapping is the hard part. In production, the firewall learns users from domain controller logs (server monitoring), GlobalProtect, or an identity provider. Every unmapped user falls into "any," so coverage matters.
    • Enable User-ID only on internal zones. Never on the internet-facing zone; it would try to identify untrusted sources.
    • Watch group mapping scope. Limit group mapping to the groups policy actually uses, so the firewall isn't reading the whole directory.
    • Mergers are a real use case. A separate zone for an acquired network, tightened with user and application rules, is a common integration pattern.
    • Other vendors: Fortinet FSSO, Cisco ISE with pxGrid, and Check Point Identity Awareness solve the same mapping problem.
    07

    Check yourself

    Why did the Source User column stay empty before task 2.4?

    The firewall only maps users in zones with User Identification enabled.

    Why use the group marketing instead of listing each marketing user?

    Membership is managed in the directory. New marketing users get access with no firewall change.

    What happens if Deny-All-Others is placed above Allow-Mktg-Apps?

    It shadows the marketing rule, and marketing users are denied too.

    What does Deny-All-Others catch that interzone-default wouldn't?

    Intrazone traffic within Acquisition, because its destination zone is any, and it logs by default.

    Why does the user filter need quotes?

    The username contains a backslash (chicago\sholmes), which must be quoted.
