Lab 4: Connecting the Firewall to Production Networks with Security Zones

Turn the firewall into a router with security boundaries. You address three Layer 3 interfaces, attach them to a virtual router with a default route, place each in its own security zone, test reachability from the firewall's CLI, and then use Interface Management Profiles to decide which interfaces answer ping and SSH.

    01

    What this lab is for

    Until now the firewall has only had a management port. This lab connects its data ports to three networks: the internet (203.0.113.0/24), your users (192.168.1.0/24), and the extranet servers (192.168.50.0/24). Every packet a user sends from here on enters one of these interfaces.

    Two ideas carry the rest of the course. First, an interface can't pass traffic until it belongs to a security zone, and zones, not interfaces, are what Security policy talks about. Second, the firewall's own data interfaces ignore ping and management traffic until an Interface Management Profile says otherwise.

    • You'll leave with: ethernet1/1 to 1/3 addressed, virtual router VR-1 with a default route, zones Internet, Users_Net, and Extranet, and two management profiles applied.
    • Builds on: Module 5, sections 5.2 to 5.5. Simulation 5.1 (zone mapper) and 5.2 (route lookup) mirror this lab.
    • Sets up: every policy lab. Lab 5 writes the first rules between these zones.

    2.2Create Layer 3 network interfaces

    Three Layer 3 interfaces: users (192.168.1.0/24), production servers (192.168.50.0/24), and the link to the upstream internet router (203.0.113.0/24).

    🧱On Firewall web interfacefirewall-a at https://192.168.1.254, in Firefox on the Client

    1. Select .
    2. Click ethernet1/1 to configure the interface.
    3. In the Ethernet Interface window, set Comment to Internet Connection, Interface Type to Layer3, and leave Virtual Router at None.
    4. Select the IPv4 tab. Leave Type set to Static. Under the IP heading, click Add and enter 203.0.113.20/24. Click OK.
    5. Click ethernet1/2 to configure the interface.
    6. In the Ethernet Interface window, set Comment to Users network connection, Interface Type to Layer3, and leave Virtual Router at None.

    2.3Create a virtual router

    You rename the predefined default virtual router to VR-1, attach the three interfaces, and give it a default route.

    🧱On Firewall web interfacefirewall-a at https://192.168.1.254, in Firefox on the Client

    1. Select .
    2. Click default to open the default router.
    3. In the Virtual Router - default window, rename the router to VR-1. Click Add to add the interfaces ethernet1/1, ethernet1/2, and ethernet1/3 (order doesn’t matter).
    4. Click Static Routes on the side. Under the IPv4 tab, click Add at the bottom of the window.
    5. In the Virtual Router – Static Route - IPv4 window, enter Name Firewall Default Gateway, Destination 0.0.0.0/0, Interface ethernet1/1, and Next Hop address 203.0.113.1. Leave the remaining settings unchanged. Click OK.

    What the default route does

    The firewall already knows its three connected networks. For every other destination, including 8.8.8.8 and every website, it needs somewhere to send the packet. The default route says “anything else goes to the ISP router at 203.0.113.1.”

    Currency: virtual routers vs. logical routers

    Since PAN-OS 10.2, firewalls can enable the Advanced Routing Engine (the Advanced Routing checkbox you saw in Lab 1’s General Settings), where routing is configured on logical routers instead. The lab uses the legacy engine and virtual routers; keep it that way here.

    Remember this route

    The capstone (Lab 14) asks for a default route named Default-Route and doesn’t give you the next hop. This is where you learn it.

    2.4Segment your production network using security zones

    An interface must belong to a zone before it can process traffic. You create three Layer 3 zones.

    3. In the Zone window, enter Name Internet, Type Layer3. Under Interfaces, click Add and select ethernet1/1. Leave all other settings unchanged. Click OK.
    4. Click Add to create a new zone.

    2.6Test interface access before management profiles

    Without an Interface Management Profile, a data interface answers neither ping nor SSH. You prove it from the client.

    🖥️On ClientZorin desktop (192.168.1.20), signed in as lab-user. Firefox, Terminal Emulator and Remmina live here.

    1. Open the Terminal Emulator on the client desktop.
    2. Issue the following command.
    Commandlab-user@client-a:~/Desktop/Lab-Files$ ping 192.168.1.1
    1. Wait a few seconds and press Ctrl+C. You get no response, because no management profile is configured yet.
    2. Attempt an SSH connection to the firewall through 192.168.1.1.
    Commandlab-user@client-a:~/Desktop/Lab-Files$ ssh admin@192.168.1.1
    1. After a few seconds, press Ctrl+C; the connection will not succeed.
    2. Leave the Terminal window open; you repeat these tests after applying a management profile. Continue to the next task.

    The failure is the lesson

    A data interface silently drops ping and management traffic addressed to it until a management profile allows it. That’s a deliberate secure default.

    The guide names the wrong interface

    Step 6 says you’ll repeat these tests after applying a profile to ethernet1/1. The tests target 192.168.1.1, which is ethernet1/2.

    2.7Define Interface Management Profiles

    Allow-ping goes on the Internet interface so SecOps can ping it from outside. Allow-mgt (ping plus HTTPS and SSH) goes on the Users_Net and Extranet interfaces.

    🧱On Firewall web interfacefirewall-a at https://192.168.1.254, in Firefox on the Client

    1. On Client: Re-open the firewall web interface by clicking the firewall-a – Mozilla Firefox icon in the task bar.
    2. Select . Click Add at the bottom of the window.
    3. In the Interface Management Profile window, enter Allow-ping for the Name. Under Network Services, check Ping. Click OK.
    4. Click Add again. Enter Allow-mgt for the Name. Under Administrative Management Services, check HTTPS and SSH. Under Network Services, check Ping, SNMP, Response Pages, and User-ID. Click OK.
    5. Select . Click ethernet1/1.
    6. In the ethernet1/1 window, click Advanced. Under Other Info, set Management Profile to Allow-ping. Click OK. ethernet1/1 will now answer ping. (In production you may not want an internet-facing interface to answer anything.)
    7. Click ethernet1/2.
    8. Click Advanced. Under Other Info, set Management Profile to Allow-mgt. Click OK.
    9. Read the Warning message and click Yes. The risk is acceptable because this is an internal network.
    10. Click ethernet1/3.
    11. Click Advanced. Under Other Info, set Management Profile to Allow-mgt. Click OK.
    12. Read the Warning message and click Yes.
    13. After steps 5 to 12, the interface table shows a management profile for each interface.

    Why the warning appears

    Allow-mgt opens HTTPS and SSH on a data interface. The firewall warns because exposing management on a network users can reach is a real risk. You accept it here because both are internal lab networks.

    Response Pages and User-ID will matter later

    Response Pages lets the firewall show block pages from ethernet1/2 (Labs 7 to 9). User-ID lets it receive user-mapping information.

    06

    How this looks on a real firewall

    • Keep management off data interfaces. Here Allow-mgt opens HTTPS and SSH on user and server networks for convenience. In production, administrative access usually stays on the dedicated management port, or on a tightly limited internal interface with permitted IPs set in the profile.
    • Be careful pinging the internet edge. Allow-ping on ethernet1/1 lets anyone on the internet confirm the firewall exists. Many organizations allow it only from their monitoring service's addresses.
    • Separate the management network. In this lab the management port (192.168.1.254) and ethernet1/2 (192.168.1.1) sit on the same subnet. Real designs keep them apart (Module 2).
    • Use more zones, not fewer. Production networks often split users, servers, guests, voice, and management into separate zones so policy can treat each differently.
    • Plan for redundancy. Production edges usually have two ISP links with path monitoring on the static routes (Module 5), or a dynamic routing protocol.

    Check yourself

    Can an interface pass user traffic if it has an IP address and is in a virtual router but no zone?

    No. Every interface must belong to a security zone before it can process traffic.

    Why does ping source 203.0.113.20 host 8.8.8.8 need a default route, but ping source 192.168.1.1 host 192.168.1.20 doesn't?

    192.168.1.0/24 is directly connected to ethernet1/2. 8.8.8.8 isn't on any connected network, so the firewall needs the default route to reach it.

    Before Allow-mgt, the client couldn't ping 192.168.1.1. Why not, if there was nothing to block it?

    Data interfaces don't answer ping or management services addressed to them unless an Interface Management Profile allows it.

    You entered 192.168.50.1 without a mask. What breaks?

    It becomes a /32, so the firewall has no connected route to the rest of 192.168.50.0/24 through ethernet1/3.

    Which zone is the client in, and which interface does its traffic enter?

    Users_Net, through ethernet1/2.
