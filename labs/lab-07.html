Lab 7: Controlling Application Usage with App-ID

Move from "allow anything between these zones" to "allow these applications." You build an application group, write a rule for the firewall's own update traffic, discover that an existing rule shadows it, fix the order, research an unfamiliar application, narrow two rules to named applications with their dependencies, and turn on the Application Block Page.

    01

    What this lab is for

    Ports no longer tell you what traffic is. Almost everything runs over TCP 443. App-ID identifies the actual application (dropbox, ms-office365, dailymotion) regardless of port, so policy can say what the business allows instead of which ports are open.

    This lab also shows rule shadowing in action. A broad rule you wrote in Lab 5 catches traffic before a more specific rule below it, and the commit warns you. And it shows why naming applications brings dependencies with it.

    • You'll leave with: the paloalto-apps group, an Allow-PANW-Apps rule in the right position, Users_to_Extranet and Users_to_Internet limited to named applications, and the Application Block Page enabled.
    • Builds on: Module 8. Simulation 8.1 explains the labels App-ID writes in the Traffic log; Simulation 6.2 rehearses shadowing.
    • Sets up: User-ID rules in Lab 11 and profile groups in Lab 8, which attach to these allow rules.

    Why the firewall's own traffic hits a Security rule here

That's a lab shortcut; in production the management network has its own path to the internet (Module 2).

    03

    Walkthrough of the detailed steps

    2.1Load the lab configuration

    Every lab starts from a known baseline, so your firewall matches the guide no matter what you did last time.

    1. On the client desktop, log in as lab-user, open Firefox, and browse to https://192.168.1.254. Log in as admin with the password from Lab Settings. If the login page does not appear, wait 1 to 3 minutes for the firewall to finish booting and refresh.
    2. Go to and click Load named configuration snapshot. Choose edu-210-11.0a-07.xml and click OK, then Close.
    3. Open Tasks (lower right) and confirm the Load task shows completed.
    4. Click Commit (upper right), then Commit in the dialog, and wait for it to finish.

    Loading is not committing

    A loaded snapshot replaces only the candidate configuration. Until you commit, the firewall is still running whatever was there before, and nothing in the lab will match the guide.

    2.2Configure an application group

    1. Go to and click Add.
    2. Name it paloalto-apps and add paloalto-dns-security, paloalto-updates, paloalto-userid-agent, paloalto-wildfire-cloud, and pan-db-cloud. Click OK.

    An example, not a full list

    The guide says so too: a production firewall may need more Palo Alto Networks applications than these five.

    2.3Configure a Security rule for firewall update traffic

    1. Go to and click Add.
    2. General: name Allow-PANW-Apps, description Allows PANW apps for firewall.
    3. Source: zone Users_Net, address 192.168.1.254.
    4. Destination: zone Internet, address Any.
    5. Application: add paloalto-apps (type the first few letters; groups appear at the end of the list).
    6. Service/URL Category: application-default and Any.
    7. Actions: Allow, Log at Session End. Click OK.
    8. The rule lands just above intrazone-default, at the bottom. Commit, and notice the commit result has a Rule Shadow tab. Close it for now.

    Positive enforcement

    You're saying exactly what the firewall's own traffic may do, rather than listing what to block. That's the model App-ID is built for.

    2.4Test the Allow-PANW-Apps rule

    1. Go to and click Check Now.
    2. In , clear filters and apply the filter below. Leave it in place.
    Log filter( app eq paloalto-updates )

    Q1: Which rule allowed the traffic?

    a. Users_to_Internet. It sits above Allow-PANW-Apps and allows any application from Users_Net to Internet, so it matches first.

    Q2: Once Users_to_Internet matches, does the firewall keep checking later rules?

    True. The first matching rule wins and evaluation stops. That's what makes Allow-PANW-Apps shadowed.

    Screenshot 1 The Traffic log showing paloalto-updates sessions matched by Users_to_Internet.

    2.5Identify shadowed rules

    1. Click Tasks (lower right) and click the Commit link for your last commit.
    2. Select the Rule Shadow tab and click the number under Count to see which rule is shadowed and by what.

    Screenshot 2 The Rule Shadow tab showing Allow-PANW-Apps shadowed by Users_to_Internet.

    2.6Fix the rule order

    1. In , select (don't open) Allow-PANW-Apps.
    2. Drag it, or use Move, so it becomes rule 3: directly below the two block rules and above Users_to_Extranet and Users_to_Internet.
    3. Commit.

    Why not move it to the very top?

    The known-bad block rules should stay first, so nothing, not even the firewall's own traffic, reaches a known-malicious address.

    2.7Test the modified rule

    1. Click Check Now in again.
    2. Reapply ( app eq paloalto-updates ). New entries now show rule Allow-PANW-Apps.
    3. In a new tab, open www.paloaltonetworks.com, then close the tab.
    4. Apply the filter below. App-ID shows the browsing as dns and ssl, allowed by Users_to_Internet.
    Log filter( addr.src eq 192.168.1.20 ) and ( rule eq Users_to_Internet )

    Screenshot 3 The Traffic log showing paloalto-updates now matched by Allow-PANW-Apps.

    2.8Generate application traffic

    1. Double-click App Generator on the client desktop and press Enter to start it. Press Enter again when it finishes, and give it 30 to 60 seconds.
    2. Apply the filter below and read the Application column.
    Log filter( addr.src in 192.168.1.20 ) and ( app neq dns )

    Q3: How should you approach applications from Users_Net to the Extranet?

    b. Allow only specific applications based on a defined policy. That's the App-ID model, and it's what task 2.10 does.

    Q4: Are there denied applications from Users_Net you should allow?

    b. Reevaluate and potentially allow specific denied applications based on security needs. Decide case by case, from business need.

    Screenshot 4 The Traffic log showing the variety of applications App Generator produced.

    2.9Research an application

    1. Filter the Traffic log for dailymotion.
    Log filter( addr.src in 192.168.1.20 ) and ( app eq dailymotion )
    1. Go to , search for dailymotion, and click its name.

    Q5: What category is dailymotion?

    c. media.

    Q6: What risk level?

    Read the Risk value on the application's entry. Palo Alto Networks can change risk ratings in content updates, so the entry on your firewall is the authoritative answer.

    Q7: Which characteristics might make you block it?

    Read the checked characteristics in the entry's Characteristics section (evasive, used by malware, capable of file transfer, prone to misuse, and so on). Answer e only if every listed option is checked on your firewall.

    Q8: What ports does it use?

    b. TCP/80,443. It's a web application, so its standard ports are HTTP and HTTPS.

    Screenshot 5 The dailymotion entry in Objects > Applications showing category, risk, and characteristics.

    2.10Narrow the rules to named applications

    1. Open Users_to_Extranet. On Application, uncheck Any and add ssl, ssh, ping, dns, ldap, radius, web-browsing. Click OK.
    2. Open Users_to_Internet. Uncheck Any and add ping, dns, ssl, yelp, web-browsing, dropbox, ms-office365.
    3. In the right pane, check the Depends On column header to select every dependency, then click Add to Current Rule. Confirm the extras now appear in the list, and click OK.
    4. Commit.

    Don't skip the dependencies

    Applications like dropbox and ms-office365 ride on other applications. Without them, the commit warns about unresolved dependencies and the applications half-work.

    Your dependency list will differ

    Palo Alto Networks updates application definitions often, so the Depends On list may not match the screenshot.

    Screenshot 6 Users_to_Internet's Application tab showing the named applications plus the added dependencies.

    2.11Test the narrowed rules

    1. Run App Generator again and let it finish. Errors and pauses are expected: the firewall is now blocking much of what it plays.
    2. Clear filters and apply the filter below to see what's being denied, mostly by interzone-default.
    Log filter( action neq allow )

    A typo in the guide's filter

    The guide prints ( action ne q allow ). The operator is one word: neq.

    Screenshot 7 The Traffic log showing denied applications after the rules were narrowed.

    2.12Enable the Application Block Page

    1. In a new Firefox tab, try http://www.shutterfly.com. It just fails to load. Close the tab.
    2. Go to and click Disabled next to Application Block Page.
    3. Check Enable Application Block Page and click OK. Commit.

    2.13Test the Application Block Page

    1. In a new tab, try http://www.shutterfly.com again, using http in Firefox. Now the firewall shows a page saying the application was blocked.

    It only works on unencrypted pages

    The firewall can't insert a page into an HTTPS session it isn't decrypting. Type http:// explicitly; Lab 12's decryption is what extends block pages to HTTPS.

    Response Pages on the interface

    The page is served from ethernet1/2, which works because Lab 4's Allow-mgt profile includes Response Pages.

    Screenshot 8 The Application Blocked page for shutterfly.com.

    App-ID reference

    Ways to name applications in a rule

    ObjectWhereUse
    ApplicationOne specific App-ID
    Application groupA fixed list you maintain, such as paloalto-apps
    Application filterA dynamic set by category, risk, or characteristic; new matching apps join automatically

    App-ID labels you'll see in the Traffic log

    LabelMeans
    incompleteThe handshake never finished; no data to identify
    insufficient-dataToo little payload to identify
    not-applicableDenied by port before App-ID ran
    unknown-tcp / unknown-udpPayload seen but matched no App-ID

    06

    How this looks on a real firewall

    • Migrate gradually. Real rulebases move from port-based to App-ID rules with Policy Optimizer (Module 8), which shows the applications each broad rule actually saw.
    • Use application filters for categories. Blocking "all file-sharing" or "risk 5" with a filter catches new applications as Palo Alto Networks adds them.
    • Give the firewall its own path. Production management traffic usually leaves through the management port or a service route (Module 2), not through user zones.
    • Plan for unknown-tcp. Unknown traffic gets its own investigation: a custom App-ID, an application override, or a block.
    • Other vendors call it something else. Fortinet has Application Control, Cisco has AVC and Snort-based app detection, Check Point has Application Control. The policy idea is the same.
    07

    Check yourself

    Why did paloalto-updates match Users_to_Internet at first?

    Users_to_Internet allowed any application and sat above Allow-PANW-Apps. First match wins.

    What's wrong with moving Allow-PANW-Apps to the very top?

    It would sit above the known-bad block rules, which should catch everything first.

    You add ms-office365 to a rule but skip Depends On. What happens?

    The commit reports unresolved dependencies and the application may fail, because it relies on other App-IDs that aren't allowed.

    Why didn't the shutterfly block page appear over HTTPS?

    The firewall can't insert a response into encrypted traffic it isn't decrypting.

    An application group or an application filter: which picks up new applications automatically?

    An application filter.
