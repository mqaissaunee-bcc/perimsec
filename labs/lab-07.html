Lab 7: Controlling Application Usage with App-ID

Move from "allow anything between these zones" to "allow these applications." You build an application group, write a rule for the firewall's own update traffic, discover that an existing rule shadows it, fix the order, research an unfamiliar application, narrow two rules to named applications with their dependencies, and turn on the Application Block Page.

    01

    What this lab is for

    Ports no longer tell you what traffic is. Almost everything runs over TCP 443. App-ID identifies the actual application (dropbox, ms-office365, dailymotion) regardless of port, so policy can say what the business allows instead of which ports are open.

    This lab also shows rule shadowing in action. A broad rule you wrote in Lab 5 catches traffic before a more specific rule below it, and the commit warns you. And it shows why naming applications brings dependencies with it.

    • You'll leave with: the paloalto-apps group, an Allow-PANW-Apps rule in the right position, Users_to_Extranet and Users_to_Internet limited to named applications, and the Application Block Page enabled.
    • Builds on: Module 8. Simulation 8.1 explains the labels App-ID writes in the Traffic log; Simulation 6.2 rehearses shadowing.
    • Sets up: User-ID rules in Lab 11 and profile groups in Lab 8, which attach to these allow rules.

    In this lab the management interface (192.168.1.254) uses the vRouter as its gateway, and the vRouter sends internet-bound traffic back through ethernet1/2. That's a lab shortcut; in production the management network has its own path to the internet (Module 2).

    App-ID reference

    Ways to name applications in a rule

    ObjectWhereUse
    ApplicationOne specific App-ID
    Application groupA fixed list you maintain, such as paloalto-apps
    Application filterA dynamic set by category, risk, or characteristic; new matching apps join automatically

    App-ID labels you'll see in the Traffic log

    LabelMeans
    incompleteThe handshake never finished; no data to identify
    insufficient-dataToo little payload to identify
    not-applicableDenied by port before App-ID ran
    unknown-tcp / unknown-udpPayload seen but matched no App-ID

    06

    How this looks on a real firewall

    • Migrate gradually. Real rulebases move from port-based to App-ID rules with Policy Optimizer (Module 8), which shows the applications each broad rule actually saw.
    • Use application filters for categories. Blocking "all file-sharing" or "risk 5" with a filter catches new applications as Palo Alto Networks adds them.
    • Give the firewall its own path. Production management traffic usually leaves through the management port or a service route (Module 2), not through user zones.
    • Plan for unknown-tcp. Unknown traffic gets its own investigation: a custom App-ID, an application override, or a block.
    • Other vendors call it something else. Fortinet has Application Control, Cisco has AVC and Snort-based app detection, Check Point has Application Control. The policy idea is the same.

    Check yourself

    Why did paloalto-updates match Users_to_Internet at first?

    Users_to_Internet allowed any application and sat above Allow-PANW-Apps. First match wins.

    What's wrong with moving Allow-PANW-Apps to the very top?

    It would sit above the known-bad block rules, which should catch everything first.

    You add ms-office365 to a rule but skip Depends On. What happens?

    The commit reports unresolved dependencies and the application may fail, because it relies on other App-IDs that aren't allowed.

    Why didn't the shutterfly block page appear over HTTPS?

    The firewall can't insert a response into encrypted traffic it isn't decrypting.

    An application group or an application filter: which picks up new applications automatically?

    An application filter.
