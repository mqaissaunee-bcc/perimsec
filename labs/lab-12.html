Lab 12: Using Decryption to Block Threats in Encrypted Traffic

Prove that encryption blinds the firewall, then fix it. You download a test virus over HTTP (blocked) and HTTPS (allowed), create forward trust and forward untrust certificates, write an SSL forward proxy rule, make the client trust the firewall's CA, block the same file over HTTPS, read the decryption evidence in the logs, and exempt sensitive categories from decryption.

    01

    What this lab is for

    Most web traffic is encrypted, and so is most malware delivery. Every profile from Labs 8 to 10 inspects content, and none of them can see content inside TLS. SSL forward proxy puts the firewall in the middle: it completes the TLS session with the client using a certificate it generates, opens its own session to the server, and inspects everything between.

    For that to work without warnings, clients must trust the CA certificate the firewall signs with (the forward trust certificate). And for sites whose own certificates are bad, the firewall signs with a second CA nobody trusts (the forward untrust certificate), so users still get a warning.

    • You'll leave with: trusted-cert and untrusted-cert, Decrypt_User_Traffic and No-Decryption rules in the right order, the firewall CA imported into Firefox, and log evidence of a decrypted, blocked threat.
    • Builds on: Module 13. Simulation 13.1 (what does the browser see?) predicts every certificate you'll meet in this lab.
    • Sets up: nothing later depends on it, but it's the lab employers ask about most.

    Walkthrough of the detailed steps

    2.1Load the lab configuration

    Every lab starts from a known baseline, so your firewall matches the guide no matter what you did last time.

    1. On the client desktop, log in as lab-user, open Firefox, and browse to https://192.168.1.254. Log in as admin with the password from Lab Settings. If the login page does not appear, wait 1 to 3 minutes for the firewall to finish booting and refresh.
    2. Go to and click Load named configuration snapshot. Choose edu-210-11.0a-12.xml and click OK, then Close.
    3. Open Tasks (lower right) and confirm the Load task shows completed.
    4. Click Commit (upper right), then Commit in the dialog, and wait for it to finish.

    Loading is not committing

    A loaded snapshot replaces only the candidate configuration. Until you commit, the firewall is still running whatever was there before, and nothing in the lab will match the guide.

    2.2See what the firewall misses without decryption

    1. In a new Firefox tab, open http://192.168.50.80/eicar.com. The connection is reset. Close the tab.
    2. In , find the entry showing the firewall blocked the eicar download.
    3. Now open https://192.168.50.80/eicar.com. At the warning, click Advanced, then Accept the Risk and Continue.
    4. When asked to save the file, click Cancel. The download wasn't blocked. Close the tab.

    Misleading task title

    The guide calls this "Examine Firewall Configuration." It's the before test: the same file over HTTP and over HTTPS.

    The whole lab in one comparison

    Same file, same server, same profiles. Over HTTP the firewall sees it; over HTTPS it can't.

    Screenshot 2 The Firefox prompt to save eicar.com over HTTPS, showing it was not blocked.

    2.3Create the forward trust certificate

    1. Go to and click Generate.
    2. Certificate Name trusted-cert, Common Name 192.168.1.1, and check Certificate Authority. Click Generate, then OK.
    3. Open trusted-cert, check Forward Trust Certificate, and click OK.

    It must be a CA

    The firewall uses this certificate to sign a fresh certificate for every site a user visits. Only a CA certificate can sign other certificates.

    2.4Create the forward untrust certificate

    1. Click Generate again. Certificate Name untrusted-cert, Common Name DO NOT TRUST, Certificate Authority checked. Generate, then OK.
    2. Open untrusted-cert, check Forward Untrust Certificate, and click OK.

    The high-level steps skip this

    Creating untrusted-cert (here) and testing it (2.9) appear only in the detailed steps. A forward proxy without an untrust certificate is incomplete: users wouldn't be warned about servers with bad certificates.

    Screenshot 3 The Certificates page showing trusted-cert as Forward Trust and untrusted-cert as Forward Untrust, both CAs.

    2.5Create the decryption policy

    1. Go to and click Add.
    2. General: name Decrypt_User_Traffic, description Decrypts web traffic from Users_Net.
    3. Source: zone Users_Net, address Any, user any.
    4. Destination: zones Internet and Extranet, address Any.
    5. Service/URL Category: Service any, URL Category Any.
    6. Options: Action Decrypt, Type SSL Forward Proxy, Decryption Profile default. Click OK, then commit.

    Why Extranet too?

    The test server, 192.168.50.80, is in the Extranet zone. Without it here, the HTTPS eicar test would never be decrypted.

    Decrypting "any" category is a starting point

    The guide notes it exposes personal data in categories like health, finance, and government. Task 2.12 adds exemptions.

    Screenshot 4 The Decrypt_User_Traffic rule with action Decrypt and type SSL Forward Proxy.

    2.6Test outbound decryption

    1. In a new tab, open https://paloaltonetworks.com. You get a warning. Click Advanced, then View Certificate.
    2. Note the Issuer: 192.168.1.1. The firewall signed this certificate on the site's behalf.
    3. Close the certificate and warning tabs (keep the firewall tab).

    Why the warning

    Firefox doesn't yet trust the firewall's CA. The certificate is technically fine; the browser just doesn't know the issuer. The next two tasks fix that.

    Screenshot 5 The certificate viewer showing www.paloaltonetworks.com issued by 192.168.1.1.

    2.7Export the firewall's CA certificate

    1. In , select (don't open) trusted-cert and click Export Certificate.
    2. File Format Base64 Encoded Certificate (PEM), uncheck Export Private Key, and click OK. Save it in Downloads.

    Never export the private key here

    Clients need only the public certificate. Anyone with the private key could impersonate every site your users visit.

    2.8Import it into Firefox

    1. Open Firefox's menu (three lines) > Settings > Privacy & Security, scroll to Certificates, and click View Certificates.
    2. On the Authorities tab, click Import, choose cert_trusted-cert.crt from Downloads, and click Open.
    3. Check both Trust this CA boxes and click OK. Confirm 192.168.1.1 appears in the list, then click OK and close Settings.

    Authorities, not Your Certificates

    CA certificates go on the Authorities tab, and the trust box must be checked. Imported anywhere else, nothing changes.

    If it isn't listed

    Click OK, then View Certificates again; the list sometimes doesn't refresh.

    Screenshot 6 Firefox's Authorities tab showing the 192.168.1.1 certificate imported.

    2.9Test the forward untrust certificate

    1. In a new tab, open https://192.168.50.80. Firefox still warns. Click Advanced, then View Certificate.
    2. The issuer is DO NOT TRUST: the firewall saw the server's self-signed certificate and passed that untrustworthiness on.
    3. Close the certificate tab and leave the warning tab open.

    The guide's note names the wrong issuer

    After step 2 the guide repeats the earlier note that the certificate was "generated by the firewall (192.168.1.1)." For this site, the issuer you should see is DO NOT TRUST, the forward untrust certificate. That's the whole point of the task.

    A warning here is correct

    The warning after importing trusted-cert proves the forward proxy isn't hiding bad server certificates from users.

    Screenshot 7 The certificate viewer showing 192.168.50.80's certificate issued by DO NOT TRUST.

    2.10Test the virus download again

    1. On the warning tab, click Accept the Risk and Continue. The server's default page loads.
    2. Change the address to https://192.168.50.80/eicar.com and press Enter. The connection fails: the firewall decrypted the session and the antivirus profile blocked the file.
    3. Close the tab.

    Two eicar paths

    The high-level steps test with www.eicar.org; the detailed steps use https://192.168.50.80/eicar.com. Either proves decryption works.

    1. Open an entry's details (magnifying glass) and confirm Decrypted is checked.

    2.12Exclude sensitive categories from decryption

    1. In , click Add. Name No-Decryption, description Do not decrypt URLs in gov, shopping and finance.
    2. Source zone Users_Net; destination zone Internet; Service any.
    3. URL Category: add government, financial-services, and shopping.
    4. Options: Action No Decrypt, Decryption Profile default. Click OK.
    5. Look at the two rules' order, answer the guide's question, then drag No-Decryption above Decrypt_User_Traffic. Commit.

    Q1: Is there anything wrong with these rules?

    a. Yes. Decrypt_User_Traffic matches any category and sits first, so No-Decryption would never be reached. No-decrypt rules always go at the top.

    Rule name drift

    The guide's answer text calls the rule "Decrypt_Users_Traffic." It's Decrypt_User_Traffic.

    Decryption reference

    The three certificates in forward proxy

    CertificateWho signs itWhen the user sees it
    Forward trust (trusted-cert, CN 192.168.1.1)Your firewall CA, trusted by clientsSites with valid certificates
    Forward untrust (untrusted-cert, CN DO NOT TRUST)A firewall CA nobody trustsSites with invalid, expired, or self-signed certificates
    The real server certificateA public CASites exempted by a No Decrypt rule

    Decryption types

    TypeProtectsNeeds
    SSL forward proxyUsers going out to any siteA CA certificate clients trust
    SSL inbound inspectionYour own serversThe server's certificate and private key
    SSH proxySSH sessionsNothing extra; controls tunneling over SSH

    06

    How this looks on a real firewall

    • Use an enterprise CA, deployed by policy. Production firewalls usually get a subordinate CA certificate from the organization's PKI, and clients trust it through Group Policy or MDM, not manual browser imports.
    • Decide exemptions with HR and legal. Which categories you don't decrypt depends on company policy, privacy law, and where users are. Health and finance are the common starting point.
    • Plan for pinned and incompatible apps. Some applications break when decrypted; Palo Alto Networks maintains a predefined exclusion list, and you'll add your own.
    • Tune the Decryption profile. The default profile allows a lot. Production profiles block expired and untrusted server certificates and weak protocol versions.
    • Size for it. Decryption is CPU-intensive; it's a real factor in choosing a firewall model.
    • Other vendors: Fortinet deep inspection, Cisco TLS server identity and decryption, and Check Point HTTPS Inspection work the same way and raise the same privacy questions.
    07

    Check yourself

    Before decryption, why did the HTTPS eicar download succeed when the HTTP one was blocked?

    The antivirus profile couldn't see the file inside the encrypted session.

    Why must trusted-cert be a Certificate Authority?

    The firewall uses it to sign a new certificate for each site, and only a CA can sign certificates.

    After importing trusted-cert, why does https://192.168.50.80 still warn?

    The server's own certificate is self-signed, so the firewall signs with the forward untrust certificate, which the browser doesn't trust.

    Why must No-Decryption sit above Decrypt_User_Traffic?

    Decryption rules are first-match; the decrypt rule matches any category, so the exemption below it would never apply.

    How do you tell from the browser whether the firewall decrypted a site?

    View the certificate. If the issuer is 192.168.1.1, it was decrypted.
